# issues — 状态核查与 Epic 编排

读写 issue 统一使用 `hack/automation/forge.sh`。写操作限于已授权的父子关联和追加 Epic 评论。执行方式由模型自行调度。

## 1. 输入与分流

- 一个或多个普通 issue 编号：进入状态核查。
- `epic #N` 或带 `epic` 标签的 issue：进入 Epic 编排。

## 2. 普通 issue 状态核查

读取 issue，结合当前代码与实现证据，判定：存在 / 已修复 / 已变更 / 无法确认。

输出各 issue 的状态、证据和建议：需要实施时建议 `/ship #N` 或定位后的 `/fix`；已修复或过期时建议关闭。

## 3. Epic 编排

### 3.1 收集任务

读取 Epic、已有子任务和相关候选，汇总任务状态、`Blocked-by`、优先级、Cx 和任务范围。

### 3.2 生成实施顺序

- 未完成任务按未完成前置的依赖层级分 Wave；已完成前置视为已满足，已完成任务单列。Wave 层数和成员数无上限。
- 同 Wave 内，根据文件、产出与消费关系及资源冲突，划分并行组或串行链，并说明冲突原因。
- 同层展示和串行定序按优先级、基础产出、Cx、issue 编号排序。
- 依赖成环或无法确认时先澄清；未完成的外部依赖标为阻塞。

### 3.3 关联与发布

呈现待关联候选和实施顺序。已有明确授权时执行；需要确认时合并为一次请求。

用 `subissue-link` 关联已授权的候选，已关联的跳过；用 `issue-comment` 追加已授权的实施顺序评论。

评论使用可见标记 `pm:epic-wave` 和纯文本格式。

## 4. 输出

- 普通 issue：编号、状态、证据、建议。
- Epic：候选及关联结果、各任务的 Wave、并行组或串行链与链内顺序、已完成任务、阻塞项。
- 已发布时附评论链接；关联或发布失败时说明原因。
