# LocalOnly proof registry 与 receipt coverage

本 runbook 说明如何读取 active LocalOnly registry、静态 effect proof 与源码登记的 runtime
conformance receipt。receipt 缺失与 provenance 违规都会阻断验证；源码登记不被
解释为本次测试已经执行。

## 生成证据

```bash
./hack/cargo.sh xtask consistency local-only-effects
./hack/cargo.sh xtask consistency report --format json > consistency-posture.json
./hack/cargo.sh xtask consistency report --format md > consistency-posture.md
./hack/cargo.sh xtask ci run --job ci-local-only \
  --required-evidence-output target/localonly-execution.json
```

静态 consistency JSON 仅输出 schema v4。调用方必须同时检查命令退出码并完整解析 JSON；采集、provenance、
结构或序列化失败时不得上传可能截断的 artifact。前两类命令只提供静态 posture/source registration；最后
一条才执行从同一 typed inventory 派生的 exact nextest suite，并只在全部成功且集合对账后发布 strict
schema v1 runtime report。

## 闭包规则

active LocalOnly 集合由 codegen 从 manifests 派生，并与
`generated::http::LOCAL_ONLY_SPECS` 及 source receipt contract ID 做 typed exact-set 对账。集合必须非空，
missing、extra、duplicate 或 equal-count-wrong-set 均 fail-closed。
Settings receipt 另闭合 provider→service→Domain mounted lineage；进程内 correctness cache upsert/remove 不算 business effect。文档不维护 receipt 实例清单。

LocalOnly 的三维 runtime observer 是 `BusinessWrite` / `Outbox` / `Publish`，对应计数键为
`business_writes` / `outbox` / `publishes`。零增长证明 handler/domain 没有业务持久化、业务 outbox 或直接
publish；correctness cache、metrics/trace、auth security audit 等 operational state 继续走专门治理，
provider-owned read-path transaction 保持允许。PostgreSQL `tenant_scoped_read*` 当前通过 transaction 绑定
tenant context；该 helper 不宣称 PostgreSQL `READ ONLY` 或稳定 snapshot。

运行 anti-vacuity 要求 active/source/executed 三个 typed ID 集合非空且彼此精确相等，同时 exact test
filter 非空。是否在某次 revision 上真实执行，必须以该次 `ci-local-only` 的 strict schema v1
报告为准，不从数量或文档清单推导。

## 证据强度与失败语义

- **Hard 上游**：codegen 只为 active LocalOnly route 生成专用 conformance marker，并生成 active
  registry；route 失活或改为非 L0 时 canonical marker 消失，receipt callsite 编译失败。
- **Medium 下游**：xtask 对每个 canonical site 闭合同一 generated module 的 marker、`SPEC` ID、mounted
  `ROUTE` typed proof、直属三维 observers、同一词法模块 `self::factory` 内“同一 routes 先 proof 后 finalize 并
  tuple 返回”的 router/proof，以及 direct generated GET operation；decoy/bait、错 route/path/method/provider、
  cfg/sibling bait、空或 wrong-but-finalized routes 均拒绝，再与 active exact-set
  对账。
- Identity 的 aggregate production lineage 只追踪 canonical `IdentityDomainDeps { ... }`、
  `IdentityDomain::new` 的不可变 destructure，以及 roles/policies 字段直接进入 production mounted state 的一层
  关系；错字段、不同 provider、mutable/alias wrapper 与 test-only Domain 均拒绝。该约束没有扩张为通用递归
  object graph。
- receipt 仅能在完整 operation await 后的 `BusinessWrite`/outbox/publish post-check 成功时由 testkit 铸造；字段和
  构造器不公开。runner-owned 私有目录仅接受 post-check 成功后写入的 strict v1 marker。
- `ci-local-only` 必须同时取得 nextest 全部成功的私有能力与 active/source/executed exact-set 的私有能力，
  report publisher 才可构造。missing、extra、duplicate、malformed、symlink、stale marker、wrong job/revision
  与 equal-count-wrong-set 均 fail-closed；不接受旧 schema、别名、JUnit 或 count-only 推导。
- duplicate、unknown、stale、marker/ID 错配、alias/wrapper、裸字符串、隐藏执行上下文、未 fail-loud
  解包或未用 `::core::assert_eq!` 断言 receipt 属于 provenance 错误并 fail-closed；缺 receipt 同样产生
  `MissingLocalOnlyReceipt`，阻断 `local-only-effects` / `verify --fast` 并令 schema v4 report `status=failed`。

该 Medium 源码证书仍只说明 canonical conformance test site 的源码闭合存在，不能说明当前 xtask 调用执行过该
测试，也不是 syscall、网络、文件系统或后台任务 sandbox。`verify --fast` 因此只保留静态证明；完整 `verify`
与 `ci-local-only` 复用同一执行 runner。报告证明受控跨进程 marker 集合在本次 suite 中闭合，仍诚实定级
Medium，不把端到端运行事实虚报为 Hard。

## 数据与安全边界

- **Static consistency v4**：仅包含 canonical contract ID、静态闭合状态、计数和 workspace-relative
  mount source；它不携带本次执行事实。
- **Runtime execution v1**：必须包含 `sourceRevision`，以及排序后的 `activeContractIds`、
  `sourceReceiptContractIds`、`executedContractIds` 三个数组；不得省略 revision identity 或退化为
  count-only 证据。

两类报告都不得包含 tenant、subject、device、请求/响应、payload、provider 错误文本、时间、主机、绝对路径
或其他敏感数据。runtime v1 的 `sourceRevision` 是绑定被执行源码所必需的 revision identity。
