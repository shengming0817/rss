# Typed Diff-Adaptive CI 运行手册（#1765、#1813）

## 当前状态

GitHub Actions 的 `CI` workflow 正常路径已收敛为 `ci-plan → execute(dynamic matrix) → ci-gate`；对应
xtask 接口为 `ci plan → ci run --job <CiJobKey> → ci gate`。唯一例外是
planner 失败时的定时 Audit 兜底。策略文件
`.config/ci-impact.toml` 使用 `mode = "adaptive"`：pull request 只执行 typed planner 推荐的受影响 job；
develop push、schedule、workflow dispatch 与显式 `RSS_CI_FORCE_FULL=true` 仍执行闭合的 typed job catalog。
这是 #1813 接受的短期风险边界：PR 优先给相关、快速反馈，每日 schedule/develop 同步承担完整回归，最长风险
窗口为一天。feature/fix/codex 分支 push 仍属 full backstop；后续可在 GitHub 成为真实 PR 入口后再删除这些
过渡 trigger。

Azure 仍是当前 forge；人工 mirror、GitHub PR 迁移和 branch protection 不属于本次代码变更。迁移完成前，
`ci-gate` 只是可观测 check，不得声称已经成为 required check。

## Canonical profile 与当前 workflow 适配边界

#1890 将 gate、test 与 journey 的主要归属收敛到闭合的 canonical `ExecutionProfile`：`check`、`test`、
`integration-critical`、`release-check`。前三者只选择自己的 primary owner，`release-check` 是所有 owner 的
集合并集，再按 typed subsumption 去重。subsumption 只表示一个 catalog execution unit 已完整覆盖另一个
unit，不是 #1883 尚未实施的测试去重。profile membership 由 typed stable-ID catalog 派生，不以
`CiJobKey`、lane 名称或 workflow matrix row 作为执行事实源。

本页所述 live workflow 尚未切换：planner 仍把选择结果兼容投影为 `CiJobKey` 动态 matrix，现有
`CiLane`、plan/evidence schema、required-evidence owner、artifact 身份和 `ci-gate` 对账协议均保持不变。
这里的 cargo-nextest `ci-core`、`integration`、`fault-matrix` profile 只控制 runner 参数和 JUnit/filter，
不等同于 canonical `ExecutionProfile`。

#1890 不删除重复测试、不缩小 integration catalog，也不创建固定 workflow Job。测试去重由 #1883 完成，
`integration-critical` 的实际关键 journey 集合由 #1884 完成，固定 `check` / `test-affected` /
`integration-critical` PR Job 与稳定聚合门切换由 #1887 完成。在这些后续任务合入前，本页以下现状与故障
语义继续有效。

## 计划与故障语义

diff-adaptive `ImpactSet` 不直接选择 stable `ExecutionUnitId`。它记录直接 package 影响、反向依赖与 coverage
闭包、integration shard、治理路径以及 docs/high-impact/unknown-path/fail-safe 状态；本地投影据此执行
固定 9 门加七域 affected 门组成的 `meta`、反向闭包 check、直接 package test/clippy 和治理自测；远端投影仍生成当前
`CiJobKey` adapter 的推荐集合。

- PR 使用 base/head 三点 diff；merge-base、NUL name-status、Cargo resolve graph、contract owner/subscriber 与
  integration execution unit 共同生成计划。
- 远端 planner 对 rename/copy、shallow history、非 UTF-8、未知路径、策略/metadata/diff 失败仍选择全量；
  本地 `make ci` 对 unknown 默认忽略并留痕，分析失败直接报错，不自动冷启动 full。
- `mandatory-full` 表示 event、Shadow、显式 override 或高影响策略要求全量；`fallback-full` 仅表示输入不确定。
- `RSS_CI_FORCE_FULL=true` 是唯一紧急回滚开关；非法值同样 fail-safe 到 `fallback-full`。
- `policyVersion` 绑定策略文件、独立行为 golden、canonical 选择的当前 `CiJobKey` 兼容投影、Integration
  shard 与路径规则；行为与 golden 不一致会令测试失败，`planDigest` 绑定本次完整计划。
- fallback 计划携带封闭的 stage、稳定错误码、可选仓库相对 subject 与操作建议；原始错误、绝对路径和
  控制字符不会进入计划或 step summary。

`ci-gate` 只在 planner 与 matrix 聚合均为 success，且 evidence v4 的 artifact/job/source revision/plan digest/
run identity 与计划执行集合完全相等时通过。LocalTx required-evidence owner `integration/postgres-domain` 在
adaptive 推荐集中也不可移除；gate 还要求其 artifact 内唯一 v3 receipt 与当前 HEAD/plan/run exact match，
并以单一 `localtxContractIds` exact-set（分别核对 active/journey/backend-profile inventory）为唯一真源（envelope 输出 `localtxContractCount`）。
failed、cancelled、skipped、缺失、重复或额外回执均失败。
LocalOnly required-evidence owner `ci-local-only` 同样始终进入计划；gate 只接受其 owner generic receipt 下唯一
`local-only/localonly-execution.json`，并把报告的 job、source revision 与当前 active/source/executed exact-set
精确绑定。两个 owner 都不得因 adaptive diff 缩小而被删除。

workflow concurrency 按 event type 与 PR/ref 隔离；schedule 不与 develop push 共享 pending slot，且仍只有 PR
run 会取消同组旧运行。正常 schedule 通过 typed full matrix 执行 Audit；若 planner 或 typed plan artifact
上传失败，统一 `ci.yml` 内的 `scheduled-audit-fallback` 仍直接执行同一个
`cargo xtask ci run --job audit` 计划。兜底不
伪造 plan/evidence，`ci-gate` 仍因 planner failure 失败，因此既保住每日供应链审计，也不会把故障运行误报为绿。

## 本地 10 分钟预算与重型任务边界

`make ci CI_BASE=<remote>/develop` 是唯一 PR 本地收尾入口，预算 600 秒。它复用 worktree 的绝对
`CARGO_TARGET_DIR` 的隔离子目录，并把 committed snapshot 按 worktree 与 HEAD 缓存在同一用户私有 Cargo cache
namespace；复用前清理所有 untracked/ignored 内容。这样既避免 launcher 与 snapshot 的不同源码路径来回改写
Cargo fingerprint，也避免随机源码路径重复失效 Rust 增量缓存。最外层 supervisor 对整个 worker 进程组施加
600 秒 wall-clock deadline，超时会终止 cargo/rustc/test 后代进程。
它只执行 `meta`、反向依赖 check、直接受影响 package test/clippy，以及 `.codex` hooks、Cargo wrapper 等定向
治理自测。`xtask` 的本地 unit-test target 只对 typed scope policy 中能证明反向消费者闭包的叶子模块投影过滤步骤；
共享模块、manifest 混合变更、任意未登记路径、全局变化或 fallback 均保守运行完整 unit target，避免 substring filter
遗漏消费者或以 0 tests 假绿。Cargo test target 的 `required-features` 直接从 metadata 进入 target identity、checkpoint 与
本地命令；hermetic 的 feature-gated target 保持 affected-local，不再因默认 feature 不可选而伪装成 remote-only。
成功 gate/stage 立即写入当前
worktree/branch 的本地 ledger；后续运行跳过已通过项，`--fresh` 清空 ledger。未进入本地计划的 full-only 工作
不输出伪步骤。
`ci-coverage` job 使用同源 `CoverageProjection`（Packages vs Workspace）；`make ci-full` 恒 Workspace——
见 [`202607260602-coverage-scope.md`](./202607260602-coverage-scope.md)。

以下任务只属于 nightly/develop 或显式人工 `make ci-full`，不得由 ship/fix/template 追加到每个本地 PR：

- workspace all-features build/clippy/default nextest；
- 全 feature matrix、全部 integration compile/live shard、全部 backend 变体；
- coverage、public-api、dylint、完整 deny/audit；
- typed catalog 已登记的 Docker/容器 integration 场景；`make docker-smoke` 仍是显式人工入口，不宣称由 nightly 承接。

## 风险接受与后续收紧

在人工 mirror 的 GitHub PR 上收集 5–10 次代表性运行，至少覆盖：纯文档、普通 Rust、adapter/integration、
contract/generated、全量 fallback。每次从 `ci-impact-plan-<run>-<attempt>` artifact 与 Job Summary 记录：

- 推荐 job 数、实际 typed job 数和 fallback 原因；
- 推荐集合之外是否出现真实失败；
- 回执集合是否完整，`ci-gate` 是否存在假通过；
- runner wall time、CPU time、预计节省 CPU time、peak RSS、磁盘和 cache 诊断。

本次 #1813 已明确接受最多一个每日同步周期的短期漏检风险，因此先启用 `adaptive`，不把 GitHub required-check
迁移作为代码激活前置条件。上述样本仍用于后续收紧：当 GitHub 成为真实 PR 入口时，再把稳定 `ci-gate` 配成
required check；动态 child 名称不得进入 branch protection。若样本出现推荐漏检或 gate 假通过，立即通过
`RSS_CI_FORCE_FULL=true` 回滚到全量执行并修复 planner。
