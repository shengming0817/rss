# L2 非一致恢复点处置

本文定义 PostgreSQL 与 RabbitMQ 已被恢复到不同时间点后，RSS 如何以受控的 same-ID recovery 收敛
OutboxFact。它只覆盖 RSS 应用状态、operator authorization 与 durable receipt，不拥有备份或恢复基础设施。

## 边界

- 外部 delivery 系统负责 PostgreSQL backup/PITR、RabbitMQ backup/数据卷恢复、维护窗口、流量切换与基础设施回滚。
- RSS 不执行或验证 PITR、RabbitMQ 数据卷恢复、Helm、Kubernetes、replica 调度或 secret projection。
- 真实后端测试只构造与 divergent restore 结果等价的 PostgreSQL/RabbitMQ 状态，证明应用恢复语义；
  该证明是 T2，不是 production process、profile 或 T3 acceptance。
- 本流程不建立 dashboard、alert、Prometheus counter、evidence database 或新的 required check。只使用现有
  health/readiness、结构化日志、operator audit 与 durable recovery receipt。

## 冻结输入

执行前必须在批准的维护窗口内冻结以下 exact 集合；任一项缺失时停止：

- operator identity、目标 tenant、change ticket 与唯一 recovery epoch；
- PostgreSQL restore point、RabbitMQ restore point 与由二者派生的闭值 recovery direction
  （`database_ahead_broker_earlier` / `broker_ahead_database_earlier`）；
- 被选择的 durable event ID 精确集合；外部 restore owner 另行冻结每条事实的 contract
  identity/fingerprint 与恢复前 absolute delivery deadline，负责物理恢复前后证据核对；
- delivery owner 冻结的 declared instance tuple 精确集合；每项为 assembly identity、verified RuntimePlan
  fingerprint 与稳定 instance UUID。RSS 只证明该声明集合全部 ack，不声称发现 deployment 全集。

两个 restore point 必须是外部 owner 已证明处于同一 UTC 时间轴的正整数 epoch microseconds，且彼此**严格
不等**；相等时 plan 构造以 `equal_restore_points` fail-closed，不存在“方向未定”的成功路径。RSS 只比较这
两个闭值来确定 direction，不据此猜测备份内容，也不从 restore point 生成 event ID、deadline 或 Inbox
状态。若任一 provider 只能提供 sequence、snapshot ID 或不同时间域的标识，外部 owner 必须先完成可信
换算/attestation；否则停止。

RSS 有意不接受调用方提供的 fingerprint、payload 或新 deadline，避免恢复命令改写 durable fact。数据库 ahead
路径只读取并锁住恢复后数据库中的 provider-owned row，验证 generated fingerprint 不漂移并保留原 absolute
deadline；本 PR 的 T2 只证明该应用内不变量，不证明物理 restore 前后的外部证据相等。broker ahead 路径的
event set 是 operator 冻结断言：不要求恢复后的 PostgreSQL outbox 存在对应行，也不得据此追加 outbox
存在性 SQL 校验。

## Operator 凭据与唯一命令

运行环境必须投影两条互不继承、无原始表权限的函数型数据库身份：auditor 只做 service-token replay 与
start/finish audit，executor 只执行已由 durable start proof 绑定的 apply。任何单条凭据都不能独立完成恢复，
grant 必须按实际动作给出精确的 `action|tenant`。闭值 action 为 `pause`、`status`、`apply`、
`resume-relay`、`resume-consumer`、`resume-writes`；不接受通配、旧变量名、明文数据库密码或命令行
service token：

```bash
export RSS_PG_L2_DR_RECOVERY_AUDITOR_USERNAME='rss_l2_dr_recovery_auditor'
export RSS_PG_L2_DR_RECOVERY_AUDITOR_PASSWORD_FILE='/run/secrets/rss-l2-dr-auditor-password'
export RSS_PG_L2_DR_RECOVERY_EXECUTOR_USERNAME='rss_l2_dr_recovery_executor'
export RSS_PG_L2_DR_RECOVERY_EXECUTOR_PASSWORD_FILE='/run/secrets/rss-l2-dr-executor-password'
export RSS_L2_DR_RECOVERY_OPERATOR_GRANTS="pause|$TENANT,status|$TENANT,apply|$TENANT,resume-relay|$TENANT,resume-consumer|$TENANT,resume-writes|$TENANT"
export OPERATOR_SERVICE_TOKEN_FILE='/run/secrets/rss-operator-service-token'
```

两角色初次启用与 retained-volume 轮换必须在 migration `0106` 后按“先停止旧 binary、后 migration、再部署全部新 binary”执行；
migration 会把 schema owner 与两条登录 lane 分开，禁止直接把 owner 开成 LOGIN。通用 `RSS_PG_HOST`、
`RSS_PG_PORT`、`RSS_PG_DATABASE`、`RSS_PG_SSL_ROOT_CERT_PATH`、`RSS_PG_MIGRATOR_*` 以及 service-token
issuer/audience/kid/secret-bundle 契约以
[`202606271438-003-container-image.md`](202606271438-003-container-image.md) 为真源（与 LocalOnly reader
provision 同级），本 runbook 只给出 L2 角色专用可复制调用，不复制第二套连接或验签配置。

1. 用待发布 operator 镜像显式 migration task 将 schema forward-only 升级到含 `0106` 的 HEAD；任务只读
   migrator 凭据，不构造 serving / L2 DR pool：

```bash
docker run --rm --entrypoint /usr/local/bin/rss \
  --env-file <non-secret-env-file> \
  --mount type=bind,src=<database-url-file>,dst=/run/secrets/pg-migration-database-url,readonly \
  --mount type=bind,src=<postgres-ca-file>,dst=/run/secrets/postgres-ca.pem,readonly \
  <operator-image> postgres migrate-all
```

   env file 只含非 Secret 配置与
   `RSS_PG_DATABASE_URL_FILE=/run/secrets/pg-migration-database-url`；密管以 `0400` 只读文件挂载 DSN 与 CA。
   DSN 必须包含口令及唯一
   `?sslmode=verify-full&sslrootcert=/run/secrets/postgres-ca.pem`，其中绝对 CA 路径必须与上面的容器 mount
   target 精确一致。

2. 在密管中生成两条互不相同的高强度密码文件后运行 provision 脚本；脚本经 `RSS_PG_MIGRATOR_*` 连接并以
   password-file 传递 auditor/executor 口令，不把秘密写入 argv、DSN 或日志：

```bash
export RSS_PG_HOST='127.0.0.1'
export RSS_PG_PORT='5432'
export RSS_PG_DATABASE='rss'
export RSS_PG_MIGRATOR_USERNAME='postgres'
export RSS_PG_MIGRATOR_PASSWORD_FILE='/run/secrets/pg-migrator-password'
export RSS_PG_L2_DR_RECOVERY_AUDITOR_USERNAME='rss_l2_dr_recovery_auditor'
export RSS_PG_L2_DR_RECOVERY_AUDITOR_PASSWORD_FILE='/run/secrets/rss-l2-dr-auditor-password'
export RSS_PG_L2_DR_RECOVERY_EXECUTOR_USERNAME='rss_l2_dr_recovery_executor'
export RSS_PG_L2_DR_RECOVERY_EXECUTOR_PASSWORD_FILE='/run/secrets/rss-l2-dr-executor-password'
# TLS 演示栈另设 PGSSLMODE=verify-full 与 PGSSLROOTCERT=<trust-anchor.pem>；容器内 psql 可设 PSQL_CONTAINER。
deploy/postgres-upgrade/provision-l2-dr-recovery-roles.sh
```

pre/post restore 均使用同一 `pause` 形态。每个 declared instance 必须逐项重复，不能由 RSS 自动发现：

```bash
rss l2-dr-recovery pause \
  --operator-service-token-stdin \
  --operator-tenant "$OPERATOR_TENANT" --tenant "$TENANT" \
  --epoch-id "$RECOVERY_EPOCH_ID" --admission-epoch-id "$ADMISSION_EPOCH_ID" \
  --change-ticket "$CHANGE_TICKET" \
  --pg-restore-point-micros "$PG_RESTORE_POINT_MICROS" \
  --rabbitmq-restore-point-micros "$RABBITMQ_RESTORE_POINT_MICROS" \
  --event-id "$EVENT_ID_1" --event-id "$EVENT_ID_2" \
  --declared-instance "runtime|$RUNTIME_PLAN_FINGERPRINT|$INSTANCE_ID" \
  < "$OPERATOR_SERVICE_TOKEN_FILE"
```

上例为 E1。E2 必须在同一命令额外加入 `--require-startup-epoch-witness`，并确保每个实例均以
`RSS_DR_REQUIRED_ADMISSION_EPOCH_ID=$ADMISSION_EPOCH_ID` 启动。该位属于同一 pause 协议的
bootstrap capability 要求，不是另一套 pre/post receipt 类型；缺少或混入 NULL witness 时 E2 不会推进到
`drained`。

`pause` 成功时必须输出 `action=pause`、本次 `admissionEpochId` / `recoveryEpochId` / `tenant`、
`phase=drained`、冻结的 `declaredInstances`、逐项对应的 `acknowledgedInstances`、
`invalidated=false`、`expired=false`、`invalidationEvidence=null`，以及非空 `expiresAtMicros`。先把整行 JSON 写入 change
record，再继续 restore；仅看到进程日志或零退出码不构成 drain receipt。

任一阶段都可用同一冻结 scope 读取 durable 状态；`status` 只读一次，不等待 phase 改变：

```bash
rss l2-dr-recovery status \
  --operator-service-token-stdin \
  --operator-tenant "$OPERATOR_TENANT" --tenant "$TENANT" \
  --admission-epoch-id "$ADMISSION_EPOCH_ID" \
  < "$OPERATOR_SERVICE_TOKEN_FILE"
```

成功输出必须为 `action=status` 的同一字段闭集；它是当前 durable snapshot，不替代对应阶段最初的 action/audit
记录。

若 `invalidated=true`，`invalidationEvidence` 由 store 返回首次拒绝的 `reason`（仅
`undeclared_instance|boot_mismatch`）及 attempted process/boot tuple；不得把它解释成 RSS 发现了额外
deployment replica。该证据只用于定位声明集或重启漂移，修复后仍必须创建全新 admission epoch。

post-restore `pause` 已返回 `drained` 后才执行 `apply`；多条事实必须逐项重复 `--event-id`，不能改用范围或通配选择：

```bash
rss l2-dr-recovery apply \
  --operator-service-token-stdin \
  --operator-tenant "$OPERATOR_TENANT" \
  --tenant "$TENANT" \
  --epoch-id "$RECOVERY_EPOCH_ID" \
  --admission-epoch-id "$ADMISSION_EPOCH_ID" \
  --change-ticket "$CHANGE_TICKET" \
  --pg-restore-point-micros "$PG_RESTORE_POINT_MICROS" \
  --rabbitmq-restore-point-micros "$RABBITMQ_RESTORE_POINT_MICROS" \
  --event-id "$EVENT_ID_1" \
  --event-id "$EVENT_ID_2" \
  < "$OPERATOR_SERVICE_TOKEN_FILE"
```

成功时 stdout 只产生一行由数据库完整 receipt row 解码并逐字段核对的 camelCase JSON。字段闭集与 direction /
outcome 闭值必须与 CLI serde 一致：

```json
{
  "epochId": "018f3c6e-7a2b-7c1d-9e4f-0123456789ab",
  "tenant": "018f3c6e-7a2b-7c1d-9e4f-0123456789ac",
  "direction": "database_ahead_broker_earlier",
  "pgRestorePointMicros": 1700000000000200,
  "rabbitmqRestorePointMicros": 1700000000000100,
  "digest": "sha256:0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef",
  "eventIds": ["event-a", "event-b"],
  "policyRevision": "same-id-delivery-v1",
  "firstStartAuditId": "018f3c6e-7a2b-7c1d-9e4f-0123456789ad",
  "appliedAt": 1700000000000300,
  "outcome": "applied"
}
```

`direction` 只允许 `database_ahead_broker_earlier` 或 `broker_ahead_database_earlier`；`outcome` 只允许
`applied` 或 `already_applied`。token、数据库密码、payload、fingerprint、deadline 和 operator subject 不进入
argv 或输出。同 epoch、同 plan 的重试可以使用新的认证和 start audit，但 `already_applied` 必须返回首次成功
receipt 的 `firstStartAuditId` / `appliedAt`（以及首次 operator subject 的 durable 证据）；任一计划字段变化
都以 epoch conflict 失败。

示例中的 `TENANT`、`OPERATOR_TENANT`、`RECOVERY_EPOCH_ID`、`CHANGE_TICKET`、两个 restore point 与每个
`EVENT_ID_n` 都来自维护窗口批准的冻结记录，不允许命令现场推导。把成功 JSON 原样写入同一 change record；没有
该行、字段与冻结计划不一致或命令非零退出时都视为未核对。

## 执行顺序

1. **Pre-restore pause。** delivery owner 停止入口扩缩容，冻结 declared instance set，创建 epoch E1 并执行
   `pause`。命令在同一线性化点关闭 Relay、Consumer、Writes，等待所有 declared boot receipt 后返回
   `drained`。将 E1 JSON 存入 change record 后停止实例；E1 不导入恢复后的数据库，也不能用于 apply。
2. **冻结计划。** 记录上述 exact 输入并复核 tenant、方向与 event ID；外部 restore owner 在自己的证据链复核
   fingerprint 与 absolute deadline。RSS 不接受范围查询、topic 通配、跨 tenant 选择或调用方提供的新 deadline。
3. **外部 restore 与 post-restore re-arm。** delivery owner 在 RSS 之外完成 PostgreSQL/RabbitMQ restore。
   为新 lineage 创建 E2；所有新实例配置 `RSS_DR_REQUIRED_ADMISSION_EPOCH_ID=E2`，在数据库出现 E2 前保持
   fail-closed。再次执行完全相同的 `pause` 协议并收齐新 boot receipts。数据库失联、未知/旧 phase、TTL
   过期都不会自动开放 lane。
4. **Apply E2。** 经 operator authorization 提交冻结的 recovery plan与 `--admission-epoch-id E2`：
   - `broker_ahead_database_earlier`：允许 broker 保留的原 ID 消息重新投递；不 reset Inbox，也不预写
     `Done`，恢复后的 ConsumerTx 按 Fresh/Duplicate 正常收敛。计划 event set 是 operator 冻结断言，不要求
     恢复后 PostgreSQL outbox 存在对应行。
   - `database_ahead_broker_earlier`：只对计划中选中的 outbox row 授权 same-ID republish；event ID、
     fingerprint 与 absolute deadline 必须与恢复后的 durable row 完全一致。deadline 已到期时在 broker I/O
     前拒绝。
5. **核对 durable receipt。** 将 stdout 的 store-sourced JSON 与冻结的 tenant、epoch、direction、两个 restore
   point、exact event set 和 digest 逐项核对，再以 `firstStartAuditId` 关联 append-only start/finish audit。
   数据库 ahead 还必须由外部 owner 核对 provider-owned fingerprint/deadline 证据；RSS 的 receipt 不冒充物理
   restore 前后证明。日志或命令退出码不能替代该 JSON + durable audit 关联。
6. **分阶段恢复 admission。** 依次执行 `resume-relay`、`resume-consumer`、`resume-writes`；每条命令只在前一
   durable phase 已完成时 CAS，并等待 declared set 对本 phase 的 boot ack。relay 已开、consumer 未开时若
   发现异常，使用新 admission epoch重新 pause，不能继续开放 consumer。ConsumerTx 继续使用既有 Inbox 与
   external-effect policy，不启用 bypass、临时 group 或新 event ID。

   三条恢复命令使用完全相同的冻结 tenant 与 admission epoch，不再携带 recovery plan：

   ```bash
   rss l2-dr-recovery resume-relay \
     --operator-service-token-stdin \
     --operator-tenant "$OPERATOR_TENANT" --tenant "$TENANT" \
     --admission-epoch-id "$ADMISSION_EPOCH_ID" \
     < "$OPERATOR_SERVICE_TOKEN_FILE"

   rss l2-dr-recovery resume-consumer \
     --operator-service-token-stdin \
     --operator-tenant "$OPERATOR_TENANT" --tenant "$TENANT" \
     --admission-epoch-id "$ADMISSION_EPOCH_ID" \
     < "$OPERATOR_SERVICE_TOKEN_FILE"

   rss l2-dr-recovery resume-writes \
     --operator-service-token-stdin \
     --operator-tenant "$OPERATOR_TENANT" --tenant "$TENANT" \
     --admission-epoch-id "$ADMISSION_EPOCH_ID" \
     < "$OPERATOR_SERVICE_TOKEN_FILE"
   ```

   每条成功 JSON 分别要求 `action=resume-relay` / `resume-consumer` / `resume-writes`，且 `phase`
   分别为 `relay_running` / `consumer_running` / `running`；其余 scope 字段必须与 `pause` receipt
   一致，`invalidated=false`，`acknowledgedInstances` 投影出的三元组精确覆盖 `declaredInstances` 且每项
   带当前 boot 证据，`expiresAtMicros` 尚未到期。每一步先保存并
   核对 receipt，再发下一条命令；`running` receipt 保存后才允许入口恢复。

### 90 秒等待与不确定结果

`pause` 与每条 `resume-*` 在 durable request 提交后，最多等待 90 秒收齐 declared instance ack；
该窗口高于 60 秒 canonical process drain budget 与 45 秒 relay publish/settle 上界。
`status` 不等待。等待超时表示“本次 CLI 未取得目标 phase receipt”，不表示数据库 request 未提交，也不得据此
推进下一阶段或换 epoch 重放 apply。立即用上面的 `status` 命令读取同一 epoch，并按以下闭值处置：

- 已到目标 phase：保存 `status` JSON，并与原命令的 timeout failure audit 一并作为本阶段 receipt；核对 scope、
  declared/acknowledged set、expiry 后才可推进。不要重发已经完成的 resume CAS。
- 仍为 `pause_requested` 或对应的 `*_resume_requested`：保持所有尚未开放的 lane，定位
  `declaredInstances - acknowledgedInstances`；不得盲目重发 resume，因为 request 可能已经持久化。
- `invalidated=true`、ack 集合与声明集合不相等、scope 不匹配或 `expiresAtMicros` 已到期：停止恢复，保存 JSON
  与 audit，使用新 admission epoch 从 pause 重新开始；不得继续 resume。
- status 缺行、数据库不可达或返回未知 phase：按 fail-closed 处理，入口保持关闭并升级给 delivery owner。

### E1 / E2 change-record checklist

Pre-restore E1 必须记录：冻结的 recovery plan digest 与 exact event set、declared instance tuples、`pause` 的
`drained` JSON、外部入口/扩缩容冻结证据，以及所有实例停止时间。E1 不得导入恢复后的 PostgreSQL，也不得传给
`apply`。

Post-restore E2 必须使用新的 admission epoch，并记录：恢复 lineage/restore point 的外部证据、所有新实例配置的
`RSS_DR_REQUIRED_ADMISSION_EPOCH_ID=E2`、E2 `drained` receipt、十一参数 fenced apply receipt、依次产生的
`relay_running` / `consumer_running` / `running` receipts，以及最后的入口恢复时间。任一 receipt 的 tenant、
recovery epoch、admission epoch、plan digest、declared set 或 expiry 与冻结记录不一致，都必须停止而不是修补记录。

## 失败与回滚

- pause、authorization、apply、audit 或 receipt 任一步失败都保持 relay/consumer 暂停；不得以人工确认把失败
  改写为成功。
- apply 失败不得留下 applied receipt 或部分选择。failure audit 是 append-only 诊断，不授权重试或扩大 event set。
- broker publish 的 ambiguous outcome 必须按“可能已接收”处理；修复连接后仍以相同 ID 和原 absolute deadline
  重试，不能通过换 ID 规避 duplicate。
- durable receipt 缺失、内容漂移、跨 tenant 命中、deadline 到期或 Inbox 被重置时立即停止。外部数据恢复需要
  回滚或重做时交还 delivery owner，RSS 不自行再次执行 PITR 或 broker restore。
- 已恢复 relay、尚未恢复 consumer 时若发现异常，重新暂停 relay；不得继续开放 consumer 观察是否自行收敛。
