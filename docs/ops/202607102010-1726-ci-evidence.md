# CI 资源证据与磁盘低水位门（#1726）

> 适用于 `.github/workflows/ci.yml` 的 typed dynamic matrix 调用
> `.github/workflows/rss-rust-lane.yml`。运行期证据由
> `.github/scripts/ci-evidence.sh` 生成，磁盘门由 `.github/scripts/ci-disk-budget.sh` 执行；
> `INVARIANT: CI-RESOURCE-EVIDENCE-01` 在 `cargo xtask verify` 中守住 workflow 时序。

## 生命周期

每个 job 使用 `${{ runner.temp }}/ci-evidence.json` 作为唯一证据文件，并按下列闭合顺序追加快照：

| 阶段 | 语义 |
|------|------|
| `start` | checkout 后、cache restore 和工具安装前的 runner/workspace 基线；随后执行磁盘门。 |
| `after-cache` | download、tool 与 compiler disk cache restore、工具准备完成后的落盘状态。 |
| `after-build` | 唯一 xtask 委托结束后的 outcome、compiler cache stats 与构建资源状态。 |
| `before-save` | writer 资格、download/tool candidate 和 save eligibility 已确定；完整 target 不参与 save。 |
| `after-save` | 显式 save 后的 step conclusion；不把 action success 声称为后端已持久化。 |

阶段重复、越级或乱序均 fail-closed。证据脚本在目标目录构造临时文件，校验闭合字段集和阶段前缀后
原子替换；追加失败、旧 JSON 损坏或目标不可写时不覆盖上一份文件。Meta 失败时由 scheduler 跳过依赖
job；统一 `ci-gate` 将缺失 snapshot/artifact 判为失败，不伪造证据。

## Evidence schema v4

顶层是严格三字段对象：

- `schemaVersion`：固定为 `4`；不接受旧 schema。
- `job`：只允许 `repository`、`workflow`、`job`、`ciJobKey`、`sourceRevision`、`planDigest`、
  `runId`、`runAttempt`、`runnerOs`、`runnerArch`，值均为字符串。后四类身份由 `ci-gate`
  与 typed plan 精确核对。
- `snapshots`：append-only 数组，始终是上述五阶段的严格有序前缀。每项只含 `stage`、`outcome`、
  `recordedAt`、`filesystem`、`directories`、`largestDirectories`、`cache`、`resourceUsage`、
  `toolVersions`、`errors`。

`filesystem` 记录 workspace 所在文件系统的 `capacityBytes`、`usedBytes`、`availableBytes`；跨 snapshot
最小 `availableBytes` 即磁盘低水位。`directories` 固定为 `workspace`、`target`、`sccache`、
`cargo-registry`、`cargo-git`、`rustup`。CI 的 `target` 指向 `$RUNNER_TEMP/rss-cargo-target`，`sccache`
指向 job-local `$SCCACHE_DIR`；不存在或 `du` 不可用时
`sizeBytes` 为 `null`，并向 `errors` 记录有限分类。

`largestDirectories` 不跟随 symlink，只测量 workspace 与 target allowlist 根的直接子目录，排除 `.git`，
并避免父子候选重复计量；结果按大小降序最多保留 20 项，逻辑路径以 `workspace/` 或 `target/` 开头。
`resourceUsage` 是闭集 `cpuTimeMs`、`peakRssBytes`，采集不可用时为 `null`。`toolVersions` 只记录
`rustc`、`cargo`、`git` 的首行版本；工具不可用时为 `null`。

`cache` 固定且仅包含：

- `download`、`tools`：字段闭集为 `restoreResult`、`restoredFootprintBytes`、`saveMode`、
  `candidateSizeBytes`、`saveOutcome`；体积是 runner 落盘值，不是网络传输量；
- `compilerCache`：字段闭集为 `enabled`、`version`、`access`、`requests`、`hits`、`misses`、
  `nonCacheable`、`errors`。`errors` 不是总数，而是严格闭合对象：`restore`、`stats`、`cacheIo`、
  `noRequests`、`measure`、`save` 六类均为 JSON 安全非负整数。启用时版本只能是 `0.15.0`，access 只能是 `local`、
  `remote-read-only` 或 `remote-read-write`；禁用时 version 为 `null`、access 为 `disabled`。

CI 使用 job-local sccache disk backend；`remote-read-only` / `remote-read-write` 只表达 Actions cache 的
restore/save 信任角色。它们不表示使用 sccache 原生 GHA backend；v0.15.0 缺少满足该矩阵的只读模式。

compiler cache stats 缺失或损坏只增加对应错误分类并呈现 degraded，不改变已有 build/test outcome；SLO
summary 与 warning annotation 必须同时暴露六类计数，且 requests/hits/misses/non-cacheable、CPU time 与
peak RSS 继续可诊断。hits 与 misses 不得超过 requests。证据不包含 cache token、endpoint、绝对 home
路径、任意环境变量或原始 stderr。

schema v4 直接拒绝 v3 和曾经的 `errors: <integer>` 形状，不提供兼容 shim；生产端与消费端必须原子升级到上述
闭合对象。
字段形状的机器单源是 `.github/scripts/testdata/ci-evidence-v4.golden.json` 与 shell selftest，不维护并行
JSON Schema。

## 磁盘预算门

`ci-disk-budget.sh --stage <name> --path "$GITHUB_WORKSPACE"` 默认要求 workspace 所在文件系统至少有
**5 GiB** 可用空间。`start` 和 `after-cache` 在工具安装及 xtask 之前 fail-fast；`after-build` 暴露构建
越过低水位；`before-save` 阻止低水位 writer 上传 cache。

阈值必须是正整数 GiB。路径不存在、`df` 缺失/失败/输出非法或空间低于阈值均非零退出，并输出稳定的
`ci-disk-budget` annotation。诊断仅使用逻辑路径和容量数值；辅助排行失败不改变主门结果。

## 安全与故障排查

artifact 使用 `actions/upload-artifact@v4` 在 `always()` 下上传 staged evidence，名称由 typed lane/job、
run ID 与 attempt 唯一确定，retention 为 7 天。`always()` 无法覆盖 checkout 前失败、runner 失联、强制
终止或平台未调度 step；这些情况不能解释为证据通过。

排查顺序：

1. 先看 `ci-disk-budget` annotation 和 job outcome，排除 runner/platform 中断。
2. 下载同一 run/attempt 的 artifact，验证 schema v4、五阶段顺序、UTC 时间、typed job、source revision 与 plan digest。
3. 对比 `filesystem.availableBytes`、target size、`resourceUsage` 和大目录排行定位资源增长。
4. 检查 `download`/`tools` 的 restore/save，再看 `compilerCache` 的 access、统计与六类 errors；不同绝对
   worktree 路径导致的 RSS crate miss 属于 sccache 0.15.0 已知 key 边界。
5. compiler cache errors 非零只会把 SLO 诊断提升为 `WARN`/`DEGRADED`，不会把正确构建改判失败；证据
   结构、原子写入、必需 `df` 或 SLO strict parser 失败仍 fail-closed。
