# CI 资源证据与磁盘低水位门（#1726）

> 适用于 `.github/workflows/ci.yml` 与 `.github/workflows/integration.yml`。运行期证据由
> `.github/scripts/ci-evidence.sh` 生成，磁盘门由 `.github/scripts/ci-disk-budget.sh` 执行；
> `INVARIANT: CI-RESOURCE-EVIDENCE-01` 在 `cargo xtask verify` 中守住 workflow 时序。

## 生命周期

每个 job 使用 `${{ runner.temp }}/ci-evidence.json` 作为唯一证据文件，并按下列闭合顺序追加快照：

| 阶段 | 位置 | 语义 |
|------|------|------|
| `start` | checkout 成功后的首个 repository-owned step | cache 恢复和工具安装前的 runner/workspace 基线；随后立即执行磁盘门。 |
| `after-cache` | `actions/cache@v4` restore 返回后、Rust toolchain 安装前 | 证明 cache 恢复对磁盘的实际影响；随后再执行磁盘门。 |
| `after-build` | 唯一 xtask 委托结束后，`always()` | 记录 `steps.xtask.outcome`（`success` / `failure` / `cancelled` / `skipped`）和构建后占用；随后执行构建后磁盘门。 |
| `before-save` | artifact 上传前，`always()` | GitHub cache post-job save 运行前最后一次 repository-owned 证据快照；不表示 RSS 显式调用 save，也不保证已观测到 post-job save 本身。 |

阶段重复、越级或乱序均 fail-closed。证据脚本先在目标目录构造临时文件，校验闭合字段集和阶段前缀后再原子 `mv`；追加失败、旧 JSON 损坏或目标不可写时不覆盖上一份文件。

共享 `setup-rss-ci` action 通过必填 `evidence-enabled` 输入表达调用契约：CI 与 Integration 在已创建 `start` 后显式传 `true`，Audit 显式传 `false`，不会进入有状态的 `after-cache` 追加路径。Cargo cache 的构建产物路径与 `.cargo/config.toml` 的 `build.target-dir` 同为 `.cache/cargo-target`。

## Evidence schema v1

顶层是严格三字段对象：

- `schemaVersion`: 固定为 `1`。
- `job`: 只允许 `repository`、`workflow`、`job`、`runId`、`runAttempt`、`runnerOs`、`runnerArch`，值均为字符串。
- `snapshots`: append-only 数组，始终是上述四阶段的严格有序前缀；正常走完尾部 step 时才包含全部四项。每项只含 `stage`、`outcome`、`recordedAt`、`filesystem`、`directories`、`largestDirectories`、`tools`、`errors`。

`filesystem` 记录 workspace 所在文件系统的 `capacityBytes`、`usedBytes`、`availableBytes`。
`directories` 固定为 `workspace`、`target`、`cargo-registry`、`cargo-git`、`rustup`；其中 `target` 的物理目录为 `CARGO_TARGET_DIR`，未设置时使用 `$GITHUB_WORKSPACE/.cache/cargo-target`。目录不存在或 `du` 不可用时 `sizeBytes` 为 `null` 并向 `errors` 记录有限的逻辑路径错误。
`largestDirectories` 不跟随 symlink，只测量 workspace 与 target allowlist 根的直接子目录，排除 `.git`，并跳过包含 target 根的 workspace 父目录，避免父子候选重复递归计量。结果按大小降序后最多保留 20 项，逻辑路径分别以 `workspace/` 或 `target/` 开头。
`tools` 仅记录 `rustc`、`cargo`、`git` 的首行版本；工具不可用时为 `null`。

字段形状的可执行单一事实源是 `.github/scripts/testdata/ci-evidence-v1.golden.json` 与 shell selftest；不存在并行 JSON Schema。

## 磁盘预算门

`ci-disk-budget.sh --stage <name> --path "$GITHUB_WORKSPACE"` 默认要求 workspace 所在文件系统至少有 **5 GiB** 可用空间。`start` 和 `after-cache` 门在工具安装及 xtask 之前 fail-fast；`after-build` 门暴露构建已经跨过低水位的情况。

阈值必须是正整数 GiB。路径不存在、`df` 缺失/失败/输出非法或空间低于阈值均非零退出，并输出稳定的 `::error title=ci-disk-budget::` annotation。低水位时诊断还会尝试列出 workspace 下深度 1 的 top-10 目录；诊断失败不会改变主门的失败结果。

## 安全边界

- 只采集上述 allowlist；禁止写入任意环境变量、完整 GitHub context、文件内容、命令行和绝对 home 路径。
- 大目录排行只保留 `workspace/` 或 `target/` allowlist 根内的逻辑相对路径，不跟随 symlink，不进入 `.git`；它仍会显示根内目录名，因此不得用 secret 命名目录。
- 脚本的 stdout/stderr 只输出固定错误、逻辑路径和容量数值；不回显传入的物理路径。

## Artifact 与故障排查

artifact 使用 `actions/upload-artifact@v4` 在 `always()` 下上传精确的 JSON 文件，不上传 runner temp 目录。名称为
`ci-evidence-${{ github.job }}-${{ github.run_id }}-${{ github.run_attempt }}`，retention 为 7 天，文件缺失时 `if-no-files-found: error` 使 job 失败。在 GitHub Actions run 的 Artifacts 区域按 job/run/attempt 下载对应 JSON。

排查顺序：

1. 先查找 `ci-disk-budget` annotation，对比 `actualGiB` 和 `requiredGiB`；若为 `df-*` 或 `path-unavailable`，先修复 runner 工具/挂载。
2. 下载 artifact，对比相邻 snapshot 的 `filesystem.availableBytes`、五个逻辑目录和 `largestDirectories`，定位 cache 恢复或构建增量。
3. 检查 `errors`。单个目录或版本采集降级不代表主 job 失败；证据文档校验、原子写入或必需的 `df` 失败则会 fail-closed。
4. 若 artifact 本身缺失，查看 checkout、runner 和上传 step 日志；不要把缺失解读为“资源正常”。

`always()` 不能突破 GitHub Actions 的执行边界：checkout 失败时不会有 `start` 证据；runner 被强制终止、进程无法调度或磁盘完全耗尽时，尾部 snapshot 和 artifact 上传也无法保证执行。
