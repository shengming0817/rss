# CI lane registry 与 `cargo xtask ci`

> 状态：CI 承载面已迁移到 GitHub Actions。Azure Pipelines 不再作为 RSS 的 CI 配置存在；Azure 仍可作为 active PR/Boards forge，但 PR/check 状态同步不在本 PR 范围。

## 架构

门逻辑单源在 Rust `cargo xtask`。GitHub workflow 只负责声明五个 literal CI job 的调度关系，
reusable workflow 负责 checkout、工具与 cache 生命周期，并精确调用对应 lane 命令；YAML 不重列低层门。

`xtask/src/ci_lanes.rs` 是 gate ID、lane、成本、编译类型、工具要求、evidence 类型与兼容聚合资格的唯一 registry。执行参数留在 `verify.rs`，但 label、工具探测和 `--fast` 编译判定都从 registry 派生，不再维护平行字段或手工 CI 清单。

- `cargo xtask verify`: stable-only 本地快门，含 fmt、治理 meta、build、clippy、nextest、deny、dylint。
- `cargo xtask ci`: 本地去重兼容聚合，复用 verify 门，build/clippy 升 `--all-features --all-targets`，Coverage 取代 Core 的 default-profile nextest，并追加 `public-api --check`；它不是六个真实 check contexts 的执行语义复刻。
- `cargo xtask ci-integration --shard <name>`: 真集成 lane 的闭合 capability shard 入口；按 shard 仅检查所需的 Postgres/Redis/RabbitMQ/Mosquitto 资源。
- `cargo xtask audit`: 定时供应链刷新 lane，跑 advisory-scoped deny + cargo-audit。

独立 lane 命令均只接受可选的 `--allow-missing-tools`；未知 flag 或尾参直接失败：

| 命令 | 内容 |
|------|------|
| `cargo xtask ci-meta` | fmt 与所有 no-compile governance gate |
| `cargo xtask ci-core` | 本地不分区完整 Core：prerequisites 与全部 tests 的精确联集 |
| `cargo xtask ci-core-prerequisites` | CI 单次执行 all-features build/clippy 与 dylint |
| `cargo xtask ci-core-tests --partition M/N` | CI 测试漏斗；必须且仅允许固定 `1/2` 或 `2/2` |
| `cargo xtask ci-security` | cargo-deny + cargo-audit |
| `cargo xtask ci-coverage` | llvm-cov + public-api |
| `cargo xtask ci-integration --shard <name>` | 指定 capability shard 的 target-level integration tests |
| `cargo xtask audit` | deny advisories + cargo-audit nightly backstop |

`cargo-audit` 是唯一 shared gate（Security 主归属、Nightly backstop 次归属，理由为闭枚举）。本地
`cargo xtask ci` 继续精确保留 46 个唯一 gate 及顺序；Core 的 default nextest 被 Coverage supersede，
因此兼容聚合不重复执行 workspace tests。该命令只作为本地聚合入口，不是 GitHub lane、job 或兼容 alias。

Registry 完整性由闭合 `GateId`、穷举映射和 const 唯一/完整断言在编译期证明（`CI-LANE-REGISTRY-01`）；lane taxonomy、shared 例外、兼容聚合与 ArchRules 绑定由带 synthetic red/anti-vacuity 的 `CI-LANE-PLAN-01` 守卫。

**INVARIANT CI-PIPELINE-DELEGATE-01**: `.github/workflows/ci.yml` 的 job 闭集精确为
`ci-meta` / `ci-core-prerequisites` / `ci-core-tests` / `ci-security` / `ci-coverage`；五者只调用同一 reusable workflow并传入 literal lane。Meta 与 Security 无依赖，Prerequisites 与 Coverage 仅 `needs: ci-meta`，Tests 仅依赖 Prerequisites，并以精确 `1/2`、`2/2` matrix 执行；禁止动态 lane、额外 job、
job-level `always()`、低层 Cargo gate 和权限扩大。对应结构化 YAML 守卫在 `xtask/src/verify.rs`。

`CI-LANE-REGISTRY-01` 通过 Rust 闭枚举、穷举 dispatch 和 const 唯一/完整断言提供 Hard 证明；
`CI-PIPELINE-DELEGATE-01` 与 lane taxonomy 通过 synthetic red、anti-vacuity 和 committed-file gate 提供
Medium 证明。不存在仅靠文档或命名约定维持的 Soft 约束。

## GitHub Workflows

| Workflow | Trigger | Command | Purpose |
|----------|---------|---------|---------|
| `.github/workflows/ci.yml` | PR / push develop + PR head branch / manual | `ci-meta`、`ci-security`；Meta 后执行 `ci-core-prerequisites` 与 Coverage；Prerequisites 后执行 Core tests `1/2`、`2/2` | 五个 job、六个实际 check contexts |
| `.github/workflows/integration.yml` | PR / push develop + PR head branch / manual | 五项 matrix 调用 `cargo run --locked -p xtask -- ci-integration --shard "$RSS_SHARD"` | 真后端 capability shards |
| `.github/workflows/audit.yml` | daily schedule / manual | `cargo run --locked -p xtask -- audit` | 未变依赖的新披露 CVE backstop |
| `.github/workflows/codeql.yml` | push develop / weekly schedule / manual | CodeQL init/analyze | SAST / code scanning |

## Nightly Pin

`public-api` 依赖 pinned nightly rustdoc-json。`PINNED_NIGHTLY`、`lints/rust-toolchain.toml` 和 `.github/workflows/ci.yml` 的 `RSS_NIGHTLY_PINNED` 必须一致，由 `pinned_nightly_single_source_of_truth` 守。

## Activation

仓库侧已提交 split workflow。首次真实 run 产生 check-run 后，从 GitHub API 读取每条 check 的实际
context 与 app ID，再原子地把旧 CI aggregate required context 替换为 `ci-meta`、`ci-core-prerequisites`、
`ci-core-tests / 1/2`、`ci-core-tests / 2/2`、`ci-security`、`ci-coverage` 六条实际 context；六条均 required。禁止按 workflow/job 显示名猜 context，
也禁止在新 contexts 可验证前删除旧 required context。迁移必须保留 Integration 与所有其它既有 required checks。

若 Azure 继续作为 active PR forge，Azure PR 与 GitHub check 状态同步由仓库运营侧另行处理；本 PR 不在
`forge.sh` 中加入同步或桥接逻辑。`CodeQL` 需要启用 code scanning（private 仓需 GitHub Advanced Security），
`Audit` 是定时漏洞刷新 backstop，不作为 PR required check。

本地命令：`make ci` 只运行 46 个唯一 gate 的兼容联集；若要复现真实 checks（包括 Core 的单次
prerequisites、两份测试 partition 与 Coverage），必须分别运行：

```bash
make ci
cargo xtask ci-meta
cargo xtask ci-core-prerequisites
cargo xtask ci-core-tests --partition 1/2
cargo xtask ci-core-tests --partition 2/2
cargo xtask ci-security
cargo xtask ci-coverage
cargo xtask ci-integration --shard postgres-domain
cargo xtask ci-integration --shard event-transport
cargo xtask ci-integration --shard runtime-http-auth
cargo xtask ci-integration --shard consistency-fault
cargo xtask ci-integration --shard cdc-projection-saga
make audit
```

Integration workflow 的 matrix 是闭合五值：`postgres-domain`、`event-transport`、
`runtime-http-auth`、`consistency-fault`、`cdc-projection-saga`，且 `fail-fast: false`，因此每个 shard
形成独立 check 与 evidence。五个并发 job 仅恢复共享 Rust cache，不具有写权限，避免同一 target cache key
被并发 writer 竞争；target taxonomy、资源需求与本地故障定位见
[`202607111214-1730-integration-shards.md`](./202607111214-1730-integration-shards.md)。

Core tests 的两个 partition 使用相同 lane/profile cache key，因此 protected `develop` push 仅指定 `1/2`
为 writer，`2/2` 恒只读；其它主 CI profile 各有单一 writer 资格。该闭集由
`CI-CACHE-WRITER-01` 的 reusable workflow guard 精确锁定，避免同 key save race。
