## 架构

门逻辑单源在 Rust `cargo xtask`。GitHub caller 只声明 `ci-plan`、`execute`、`ci-gate` 三个顶层 job：
planner 从闭合 `CiJobKey` 生成动态 matrix，唯一 executor 调用 reusable workflow，稳定 gate 聚合结果与回执。
reusable workflow 负责 checkout、工具与 cache 生命周期，并精确调用对应 lane 命令；YAML 不重列低层门。

`xtask/src/ci_lanes.rs` 是 gate ID、lane、成本、编译类型、工具要求、evidence 类型、兼容聚合资格和
14 个 `CiJobKey` 的唯一 registry。执行参数留在 `verify.rs`，但 label、工具探测、`--fast` 编译判定及
reusable lane 闭集都从 registry 派生；workflow 只保留跨 GitHub Actions 边界所需的 dispatch adapter。

- `cargo xtask verify`: stable-only 本地快门，含 fmt、治理 meta、build、clippy、nextest、deny、dylint。
- `cargo xtask ci`: 本地去重兼容聚合，复用 verify 门，build/clippy 升 `--all-features --all-targets`，Coverage 取代 Core 的 default-profile nextest，并追加 `public-api --check`；它不是 typed planner 的 14-job 动态执行语义复刻。
- `cargo xtask ci-integration --shard <name>`: 真集成 lane 的闭合 capability shard 入口；按 shard 仅检查所需的 Postgres/Redis/RabbitMQ/Mosquitto 资源。
- `cargo xtask audit`: 定时供应链刷新 lane，跑 advisory-scoped deny + cargo-audit。

独立 lane 命令均只接受可选的 `--allow-missing-tools`；未知 flag 或尾参直接失败：

| 命令 | 内容 |
|------|------|
| `cargo xtask ci-meta` | fmt 与所有 no-compile governance gate |
| `cargo xtask ci-core` | 本地不分区完整 Core：prerequisites 与全部 tests 的精确联集 |
| `cargo xtask ci-core-prerequisites` | CI 单次执行 all-features build/clippy 与 dylint |
| `cargo xtask ci-core-tests --partition M/N` | CI 测试漏斗；必须且仅允许固定 `1/2` 或 `2/2` |
| `cargo xtask ci-security` | cargo-deny + cargo-audit |
| `cargo xtask ci-coverage` | llvm-cov + public-api |
| `cargo xtask ci-integration --shard <name>` | 指定 capability shard 的 target-level integration tests |
| `cargo xtask audit` | deny advisories + cargo-audit nightly backstop |

`cargo-audit` 是唯一 shared gate（Security 主归属、Nightly backstop 次归属，理由为闭枚举）。本地
`cargo xtask ci` 继续执行 registry 派生的唯一 gate 联集与顺序；Core 的 default nextest 被 Coverage supersede，
因此兼容聚合不重复执行 workspace tests。该命令只作为本地聚合入口，不是 GitHub lane、job 或兼容 alias。

Registry 完整性由闭合 `GateId`、穷举映射和 const 唯一/完整断言在编译期证明（`CI-LANE-REGISTRY-01`）；lane taxonomy、shared 例外、兼容聚合与 ArchRules 绑定由带 synthetic red/anti-vacuity 的 `CI-LANE-PLAN-01` 守卫。

**INVARIANT CI-ADAPTIVE-WORKFLOW-01**: `.github/workflows/ci.yml` 的 job 闭集精确为
`ci-plan` / `execute` / `ci-gate`。planner 从 `CiJobKey` 派生非空动态 matrix，executor 只调用同一
reusable workflow，`ci-gate` 在 `always()` 下验证聚合结果与 evidence v4 回执；禁止静态复制 lane/shard、
path filter、PR 分支 push、额外 job 和权限扩大。对应结构化 YAML 守卫在 `xtask/src/verify.rs`。

`CI-LANE-REGISTRY-01` 通过 Rust 闭枚举、穷举 dispatch 和 const 唯一/完整断言提供 Hard 证明；
`CI-ADAPTIVE-WORKFLOW-01` 与 lane taxonomy 通过 synthetic red、anti-vacuity 和 committed-file gate 提供
Medium 证明。不存在仅靠文档或命名约定维持的 Soft 约束。

## L0/L1 Verification Boundary

本地 canonical 入口使用 `make` 或 `./hack/cargo.sh xtask`；精确 gate 成员与顺序只由 typed registry 派生，
本节不复制低层 inventory：

| 层级 | Canonical 入口 | 证明边界 |
|------|----------------|----------|
| Fast | `make verify-fast` | 无需编译的 contract、codegen 与 L0/L1 静态闭包；不证明行为或真实后端 |
| Full | `make verify` | 增加编译、默认行为测试与 integration target 编译；不执行真实 integration |
| Live | `./hack/cargo.sh xtask ci-integration --shard postgres-domain` | 实跑 Postgres LocalTx matrix 与 active L1 journey |

最终 closeout 证据不得使用 `--allow-missing-tools`；缺 nextest、Docker 或 shard 所需资源应保持 fail-closed。
L0/L1 采用顺序与业务故障语义分别由 [`../rules/consistency-l0.md`](../rules/consistency-l0.md) 与
[`../rules/localtx.md`](../rules/localtx.md) 持有。

## Activation

仓库侧已提交 Shadow workflow。完成代表性样本并迁移 GitHub PR 后，从 GitHub API 读取 `ci-gate` 的实际
context 与 app ID，将其配置为唯一自适应 CI required context；动态 child 名称不得进入 branch protection。
在 `ci-gate` 已验证且 required 前不得切换 `.config/ci-impact.toml` 到 `adaptive`。动态 `execute` child
名称随 matrix 变化，不能配置为 required checks；branch protection 只绑定稳定的 `ci-gate` context。

若 Azure 继续作为 active PR forge，Azure PR 与 GitHub check 状态同步由仓库运营侧另行处理；本 PR 不在
`forge.sh` 中加入同步或桥接逻辑。`CodeQL` 需要启用 code scanning（private 仓需 GitHub Advanced Security），
`Audit` 是定时漏洞刷新 backstop，不作为 PR required check。

本地命令：`make ci` 只运行 registry 派生的兼容联集，并不复现 planner、14 个独立 runner、artifact
回执或 gate 聚合。若要逐项复现 Shadow 完整 catalog 的 lane 命令（不含 GitHub 调度/证据边界），运行：

```bash
make ci
./hack/cargo.sh xtask ci-meta
./hack/cargo.sh xtask ci-core-prerequisites
./hack/cargo.sh xtask ci-core-tests --partition 1/2
./hack/cargo.sh xtask ci-core-tests --partition 2/2
./hack/cargo.sh xtask ci-security
./hack/cargo.sh xtask ci-coverage
./hack/cargo.sh xtask ci-integration --shard postgres-domain
./hack/cargo.sh xtask ci-integration --shard event-transport --partition 1/2
./hack/cargo.sh xtask ci-integration --shard event-transport --partition 2/2
./hack/cargo.sh xtask ci-integration --shard runtime-http-auth --partition 1/2
./hack/cargo.sh xtask ci-integration --shard runtime-http-auth --partition 2/2
./hack/cargo.sh xtask ci-integration --shard consistency-fault
./hack/cargo.sh xtask ci-integration --shard cdc-projection-saga
make audit
```

14 个 `CiJobKey` 由 6 个非 Integration job、7 个 Integration rows 和 1 个 Audit job 组成。Integration
rows 覆盖 `postgres-domain`、`consistency-fault`、`cdc-projection-saga` 三个不分区 shard，以及
`event-transport`、`runtime-http-auth` 各两个 hash partition。caller 使用 `fail-fast: false`，因此每个 row
形成独立动态 child 与 evidence；这些 child 只恢复共享 Rust cache，不作为 required checks。target taxonomy、
资源需求与本地故障定位见
[`202607111214-1730-integration-shards.md`](./202607111214-1730-integration-shards.md)。

Core tests 的两个 partition 使用相同 lane/profile cache key，因此 protected `develop` push 仅指定 `1/2`
为 writer，`2/2` 恒只读；其它主 CI profile 各有单一 writer 资格。该闭集由
`CI-CACHE-WRITER-01` 的 reusable workflow guard 精确锁定，避免同 key save race。
