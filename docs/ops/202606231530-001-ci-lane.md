# CI lane：`cargo xtask ci` 全门上 Azure Pipelines（issue #1132 + 供应链门 #1133）

> 状态：v1 落地（#1132 主门）+ 供应链 advisory 定时刷新 lane（#1133）。realizes（兑现）归档计划
> `docs/migration-from-gocell/gocell-rust-ci-plan.md` 的 Rust 门集映射（含 `security-vuln→cargo-deny advisories+cargo-audit`）。

## 动机

此前 `AZURE_HAS_CI=false`、仓库无任何 CI 配置——治理全靠人记得本地 `make verify`。AI 协作下**无自动门**，
签名漂移 / 治理回归只能事后人查（issue #1132 评级 **Medium**：把治理从 Soft「人记得」上移到 Medium「CI 门」，
本 Feature 最高杠杆项）。本 PR 在 Azure DevOps（实际 forge，PR 与合并策略都在此）落一条 PR 触发、失败阻断
合入的 CI lane。

## 架构：薄 YAML 委托 `cargo xtask ci`

门逻辑单源在 Rust（`cargo xtask`），CI YAML 只装 toolchain/工具再调一条聚合命令——本地 `make ci` ≡ CI。

- **`cargo xtask verify`**（不变）：stable-only 本地快门。fmt + contract-validate + layer-deps + codegen-check
  + build(`--workspace`) + clippy(`--workspace --all-targets`) + nextest + deny + dylint。
- **`cargo xtask ci`**（新增，CI lane 唯一入口）：verify 全门，但 build/clippy 升 `--all-features --all-targets`
  （编译态全覆盖，含 integration-gated 代码——仅编译不运行 ⇒ 无需 DB/broker）；**覆盖率门替 nextest**
  （`cargo llvm-cov nextest --workspace` 单跑一次既是 nextest 门又出覆盖率）；尾追 `public-api --check`（轴 A）。
- `verify` 与 `ci` 经 `full_plan()` / `ci_plan()` 共享 fmt/meta/deny/dylint 同一构造，杜绝两份计划漂移
  （`xtask/src/verify.rs`）。

**INVARIANT CI-PIPELINE-DELEGATE-01**：`azure-pipelines.yml` 只调 `cargo xtask ci`、不在 YAML 里逐条重列门
run 命令；由 `xtask` 治理测试 `azure_pipeline_delegates_to_xtask_ci` 守（防 YAML 与 xtask 单源漂移）。

## 门 → issue #1132 验收映射

| 验收项 | 兑现 |
|--------|------|
| `cargo build --workspace --all-features --all-targets` | ci `build` 步 |
| `cargo fmt --check` + `cargo clippy --all-targets --all-features -- -D warnings` | ci `fmt` / `clippy` 步 |
| `cargo nextest run --workspace` | ci `coverage` 步（llvm-cov 包 nextest，测试全绿才过） |
| `cargo llvm-cov` 阈值门（引擎/基础 ≥90%） | ci `coverage` 步 per-crate 下限（见下） |
| `cargo xtask verify` 聚合（insta golden / dylint / deny / layer-deps / contract validate / codegen drift） | ci 复用 verify 全门（insta golden = nextest 跑 snapshot 测试 + codegen-check 字节门） |
| `cargo public-api` / `cargo-semver-checks`（轴 A） | ci `public-api` 步（semver-checks 见「取舍」） |
| PR 触发 + 失败阻断合入 | Azure 分支策略 build validation（见 runbook） |

## 覆盖率门（per-crate 下限 + ratchet）

`coverage.rs`：跑 `cargo llvm-cov nextest --workspace --json` → 解析 export JSON → 按 crate 聚合行覆盖率。
STRICT 集 = CLAUDE.md「引擎与基础 crate ≥90%」逐字集 `vocab/ids/consistency/primitives`。

- 默认下限 **90%**：`vocab` / `ids` / `primitives` 均超 90%（实际值以 CI 报告为准，不在文档固化快照以免漂移）。
- **ratchet 例外**：`consistency` 当前未达 90%——其 L3/L4 接缝（`saga`/`reconcile`/`projection`）仍是签名冻结
  `todo!()` 桩（「行为 PR 兑现」，无法测——调用即 panic），**非测试债**（已实现的 idempotency/outbox/error 高覆盖）。
  故暂设 ratchet 下限 **85%**（thaw 余量），待接缝兑现+测试落地 restore 90%（follow-up #1146）。`RATCHET_FLOORS`
  只含 consistency，由 `ratchet_floors_only_consistency` 测试守不被静默扩容。
- **anti-vacuity**（COVERAGE-STRICT-FLOOR-01）：STRICT crate 未被测量（JSON 无数据 / 0 行）也 fail，杜绝
  「没跑到 = 静默绿」。

## 取舍：semver-checks 本轮不入

`cargo-semver-checks`（轴 A 语义破坏检测）当前**不入 ci**：全 workspace crate 均 `publish = false`，
`cargo semver-checks --workspace` 选 0 个可发布包 ⇒ 门**空转**（违反 anti-vacuity，不能 ship 静默绿门）。
轴 A 由 **`public-api --check`**（committed baseline 漂移门，basis+engine 7 crate，非空转）兜住。待 crate
可发布 / 采用显式 unpublished 处理后 follow-up 接入。

## 供应链安全门 lane（issue #1133）

`cargo deny check`（PR 门 ci 内）本已一把抓 **advisories(RustSec) + licenses + bans + sources**，每 PR 跑、失败
阻断——即 #1133 验收①③已由 #1132 主门兑现。#1133 补两块**净增**能力：

1. **cargo-audit 入门（防御纵深）**：`step_cargo_audit`（`cargo audit`）加入 ci（PR 阻断门）。与 deny advisories
   同查 RustSec 的**独立第二实现**——防 deny.toml advisories 被误改架空。朴素形（仅漏洞致非零、unmaintained/yanked
   仅 warn）与 deny advisories 的 vuln-deny 语义对齐，避免一门红一门绿。
2. **每日定时刷新 lane（时间维度）**：`cargo xtask audit`（advisory-scoped `deny check advisories` + cargo-audit
   两门，皆 no-compile、快）经 `azure-pipelines.yml` 的 `schedules:` cron 每日跑。PR 门只在 PR 上跑——对**未变
   依赖**新披露的 RustSec CVE 要等下个 PR 才捕获；定时刷新填这个盲区（替代 gocell `security-vuln.yml` 定时 workflow）。
   `always: true` 保证无代码变更也跑。

**Build.Reason 条件分流**（单 YAML 文件）：PR/push（`ne(Build.Reason,'Schedule')`）→ 全量 `cargo xtask ci`；
每日 Schedule（`eq(...,'Schedule')`）→ lean `cargo xtask audit`。安装步不按 reason 条件化（缓存热路径成本低；
定时 lane 精简安装留作可选 follow-up）。

**lane 语义**：PR 门 ci = **合入阻断**（Azure build validation）；定时 audit lane = **告警**（无 PR 可阻断，
红即 Azure 通知 → 人工接力）。INVARIANT CI-PIPELINE-DELEGATE-01 同族：YAML 只调 `cargo xtask audit`（不内联
`cargo deny`/`cargo audit`），由治理测试 `azure_pipeline_has_scheduled_audit_lane` 守。

**双工具 ignore 对账**（守卫 `deny_audit_ignore_lists_reconciled`，Medium）：deny（feature-resolved 图）与
cargo-audit（扫 Cargo.lock 全量）各有独立 ignore。不变式 = **deny.toml.ignore ⊆ cargo-audit `--ignore`**：deny
接受的任一**图内** advisory 必须同步到 cargo-audit，否则一过一红。反向 audit 可多 ignore（phantom-only）。
当前唯一 audit 侧 ignore = **RUSTSEC-2023-0071**（rsa Marvin Attack）：rsa 是 phantom Cargo.lock 条目（经
sqlx-mysql，mysql feature 未启用）——`cargo tree -i rsa --all-features --target all` 为空 ⇒ 任何 feature/target
下都不编译进产物、无暴露面，且无修复版本；deny advisories（按图）本就不报，故仅 cargo-audit 侧 ignore。
**phantom 论证由机器守卫锁住**（非 Soft）：`deny.toml [bans]` 加 `{ crate = "rsa" }`——rsa 一旦进入
feature-resolved 依赖图（如启用 mysql feature），`cargo deny check bans` 即非零退出，强制显式决策（移除 ban +
重评漏洞 + 同步 cargo-audit ignore）；图外时为 no-op。

### 交付边界 / 激活前状态

`schedules:` cron 与 PR 阻断一样**须先完成激活 runbook（pipeline-create + pipeline-policy）才生效**——本 PR
交付的是 **YAML + lane 机制 + runbook**，非「合入即生效的定时刷新」。`AZURE_HAS_CI=false` 期间定时刷新能力为零，
**时间盲区由本地 `make audit` 手动弥补**（同 #1132「commit YAML ≠ 保护即生效」）。
工具经 `cargo binstall` 取预编译二进制（含 cargo-audit），信任模型 = TLS + Microsoft-hosted agent，**不校验二进制
哈希**（同 #1132 既有模型，本 PR 不改变）——供应链门工具自身的更强完整性保证（源码编译 / 哈希钉定）登记 #1145。

## 激活 runbook（org 侧一次性，仓库无法代办）

本 PR 交付 CI lane + 机制；Azure org 侧启用是一次性环境动作。先留 `AZURE_HAS_CI=false`（避免翻 true 后
ship/fix 的 ci-watch 空转）。步骤（亦见 `hack/automation/forge.conf` 注释）：

1. 申请 Microsoft-hosted 免费并行额度（私有项目需提交表单 https://aka.ms/azpipelines-parallelism-request ，~2-3 工作日）或挂自托管 agent。
2. 注册 pipeline（verb 签名 `pipeline-create <name> <repo> <branch> <yaml> [queue-id]`）：
   `bash hack/automation/forge.sh pipeline-create rss-ci rss develop azure-pipelines.yml`
3. 给 `develop` 设 build validation = PR 触发 + 失败阻断合入（`pipeline-policy <name> <repo> <branch> <display-name>`）：
   `bash hack/automation/forge.sh pipeline-policy rss-ci rss develop "RSS CI"`
4. 把 `forge.conf` 的 `AZURE_HAS_CI` 改成 `true`。
5. 开测试 PR 验证全链路（pipeline 跑 `cargo xtask ci`、失败阻断、ship/fix 贴 pm:ci）。
