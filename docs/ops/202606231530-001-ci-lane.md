## 架构

执行成员的规范模型在 Rust `cargo xtask` 中。闭合 `ExecutionProfile` 只有四个值：

| Profile | 规范语义 |
|---------|----------|
| `check` | 只选择 primary owner 为 `check` 的静态检查与治理单元。 |
| `test` | 只选择 primary owner 为 `test` 的组件/测试单元。 |
| `integration-critical` | 只选择 primary owner 为 `integration-critical` 的关键接缝与 journey。 |
| `release-check` | 全部 primary owner 的集合并集，再按 typed subsumption 去重；用于完整验证，不是 Cargo release build profile 或制品发布流程。 |

每个 gate、test 或 journey 只有一个 primary owner；profile membership 从 stable-ID catalog 与 owner 集合关系
派生，不维护另一份 raw 列表。`release-check` 的全量语义由 owner 集合并集后应用 typed subsumption 得到，
当前条目数量不是协议。subsumption 只表达一个 catalog execution unit 已完整覆盖另一个 unit；它不等于、也不
提前实施 #1883 对重复测试执行的裁剪。

以下名字处在不同层，不能互相替代：

| 类型 | 职责 |
|------|------|
| canonical `ExecutionProfile` | 定义执行单元的唯一主要归属和规范集合。 |
| cargo-nextest `NextestProfile` | 配置 retry、timeout、JUnit、runner filter 等工具行为，不拥有跨工具测试集合。 |
| `CiJobKey` / `CiLane` | 当前 live GitHub workflow 的 dispatch、partition、artifact 与 evidence 身份适配器。 |
| `ImpactSet` | 闭合的路径影响模型；记录 package 影响、反向依赖闭包、integration shard、治理路径及 fail-safe 状态，再分别投影到本地执行和当前 `CiJobKey` 适配器。 |

GitHub caller 目前仍只声明 `ci-plan`、`execute`、`ci-gate` 三个顶层 job：planner 将规范选择结果兼容投影成
闭合 `CiJobKey` 动态 matrix，唯一 executor 调用 reusable workflow，稳定 gate 聚合结果与回执。reusable
workflow 负责 checkout、工具与 cache 生命周期，并只调用 `cargo xtask ci run --job <CiJobKey>`；YAML
不重列低层门或拼装 lane 命令。

`xtask/src/ci_lanes.rs` 继续持有 gate stable ID、成本、编译类型、工具要求、evidence 类型以及当前
`CiJobKey` / `CiLane` 适配信息；它们的执行成员必须从 canonical profile 投影，不再反向定义 profile。
执行参数留在 `verify.rs`，workflow 只保留跨 GitHub Actions 边界所需的 dispatch adapter。

- `cargo xtask ci local --base <ref>`：只分析 `<ref>...HEAD` 的已提交项目差异，由 `ImpactSet` 的本地投影执行 preflight。
- `cargo xtask ci full`：无条件执行原完整本地 CI 门集（coverage 恒 `CoverageScope::Workspace`）。
- `cargo xtask ci plan ...`：从同一 `ImpactSet` 生成远端推荐 `CiJobKey` 集合与动态计划。
- `cargo xtask ci run --job <CiJobKey>`：唯一远端 typed executor，由闭合 enum 穷举分派；
  `ci-coverage` 用与 plan 同 base 的 `CoverageProjection`（Packages 或 Workspace）。
- `cargo xtask ci gate ...`：核验聚合结果与 evidence v4 回执。

空的 `cargo xtask ci`、旧平铺入口、未知或重复参数均 fail-closed。`verify` / `verify --fast`、`ci full`
及当前 typed job 都通过兼容投影复用 canonical profile，不维护第二份成员表。常用接口：

| 命令 | 内容 |
|------|------|
| `make ci [CI_BASE=<ref>]` | 受控 bootstrap；默认 `origin/develop...HEAD` 的本地差异 preflight |
| `make ci-full` | 受控 bootstrap；完整本地 CI 门集（含 Workspace coverage） |
| `cargo xtask ci run --job ci-coverage` | 按 CoverageProjection 跑 llvm-cov（Packages 或 Workspace）+ STRICT 条件地板 + diffcov |
| `cargo xtask ci run --job ci-local-only --required-evidence-output <path>` | 执行唯一 LocalOnly required-evidence owner，并在 active/source/executed exact-set 后发布 v1 报告 |
| `cargo xtask ci run --job integration/postgres-domain` | 执行一个闭合 Integration job |
| `cargo xtask ci run --job audit` | deny advisories + cargo-audit nightly backstop |

`cargo-audit` 只有一个 canonical primary owner；当前兼容适配器把同一执行单元投影到依赖变更时的 Security
执行与定时 Nightly backstop，不复制 gate。其它本地和远端选择同样不维护第二份路径映射：私有构造的
`ImpactSet` 同时携带直接 package 影响（含 contract owner/subscriber）、反向依赖与 coverage 闭包、
integration shards、治理路径以及 docs/high-impact/unknown-path/fail-safe full 状态。本地投影运行 fast/meta、
反向闭包 check、直接 package test/clippy 与治理自测，并将 integration shard 留为 deferred；远端投影按
package reason 和 integration shard 生成当前 `CiJobKey` 推荐集合。它当前不选择或投影 stable
`ExecutionUnitId`。

执行 profile 与 registry 的完整性由 Rust 代码及其 typed tests 证明；本文只解释运维语义，不是 enforcement
carrier。现有 lane taxonomy、shared 例外、兼容聚合与 ArchRules 绑定仍由对应代码不变式守卫。

**INVARIANT CI-ADAPTIVE-WORKFLOW-01**: `.github/workflows/ci.yml` 的 job 闭集精确为
`ci-plan` / `execute` / `ci-gate`。planner 从 `CiJobKey` 派生非空动态 matrix，executor 只调用同一
reusable workflow，`ci-gate` 在 `always()` 下验证聚合结果与 evidence v4 回执；禁止静态复制 lane/shard、
path filter、PR 分支 push、额外 job 和权限扩大。对应结构化 YAML 守卫在 `xtask/src/verify.rs`。

`CI-LANE-REGISTRY-01` 通过 Rust 闭枚举、穷举 dispatch 和 const 唯一/完整断言提供 Hard 证明；
`CI-ADAPTIVE-WORKFLOW-01` 与当前 workflow adapter 通过 synthetic red、anti-vacuity 和 committed-file gate
提供 Medium 证明。canonical profile membership 不由本页表格或措辞强制。

## L0/L1 Verification Boundary

本地 canonical 入口使用 `make` 或 `./hack/cargo.sh xtask`；精确成员由 canonical profile 与 typed stable-ID
registry 派生，兼容入口只决定投影和执行顺序。本节不复制低层 inventory：

| 层级 | Canonical 入口 | 证明边界 |
|------|----------------|----------|
| Local | `make ci CI_BASE=<remote>/develop` | 10 分钟有界 affected preflight：fast/meta、反向闭包 check、直接包 test/clippy 与定向治理自测；feature/integration/workspace 重门 `DEFERRED` 到 nightly/develop |
| Full | `make ci-full` | 无条件执行当前完整本地 CI 门集 |
| LocalOnly | `./hack/cargo.sh xtask ci run --job ci-local-only --required-evidence-output <path>` | 从静态 typed inventory 派生 exact nextest filter；全部测试成功且 active/source/executed 集合完全相等后发布唯一 v1 report |
| Live | `./hack/cargo.sh xtask ci run --job integration/postgres-domain` | CI typed executor；实跑 Postgres LocalTx matrix 与 active L1 journey |

最终 closeout 证据不得使用 `--allow-missing-tools`；缺 nextest、Docker 或 shard 所需资源应保持 fail-closed。
L0/L1 采用顺序与业务故障语义分别由 [`../rules/consistency-l0.md`](../rules/consistency-l0.md) 与
[`../rules/localtx.md`](../rules/localtx.md) 持有。

## Activation

#1890 的激活仅发生在 `xtask` 内部：现有命令、`CiJobKey` wire、plan/evidence schema、artifact 名称、required-
evidence owner、dynamic child context 与 workflow topology 保持不变。`make ci` 继续运行受影响预检；完整本地
聚合继续由 `make ci-full` 触发并使用当前 compatibility projection；它不会冒充已经执行了尚未切换的完整
`release-check` integration catalog。

后续变更按依赖顺序独立交付：#1883 冻结测试唯一 owner 并删除 workspace/backend/assembly 重复执行；#1884
再定义小而稳定的 `integration-critical` 集合，并把完整 integration catalog 留给 develop/nightly/
`release-check`；#1887 最后把远端动态 matrix 切成固定 `check`、`test-affected`、`integration-critical` Job。
本阶段不得据 canonical 名称提前声称这些范围缩减或 workflow 切换已经生效。

仓库侧已按 #1813 接受最长一个每日同步周期的短期风险并启用 adaptive。迁移 GitHub PR 后，从 GitHub API 读取
`ci-gate` 的实际 context 与 app ID，将其配置为唯一自适应 CI required context；动态 `execute` child 名称随
matrix 变化，不能配置为 required checks。required check 收紧是后续运营动作，不得反向声称当前已阻断 Azure 合入。

若 Azure 继续作为 active PR forge，Azure PR 与 GitHub check 状态同步由仓库运营侧另行处理；本 PR 不在
`forge.sh` 中加入同步或桥接逻辑。`CodeQL` 需要启用 code scanning（private 仓需 GitHub Advanced Security），
`Audit` 是定时漏洞刷新 backstop，不作为 PR required check。

本地 canonical 命令只走 `ImpactSet` 的本地投影，不复现 GitHub 调度、artifact 回执或 gate 聚合。
完整本地门集与远端 typed job 的显式入口分别为：

```bash
make ci CI_BASE=origin/develop
make ci-full
./hack/cargo.sh xtask ci run --job ci-meta
./hack/cargo.sh xtask ci run --job ci-core-tests/1-of-2
./hack/cargo.sh xtask ci run --job ci-local-only --required-evidence-output target/localonly-execution.json
./hack/cargo.sh xtask ci run --job integration/postgres-domain
./hack/cargo.sh xtask ci run --job audit
```

job taxonomy 与 Integration row 集合由 typed registry 和 shard projection 精确派生，不在运维文档复制
当前目录。caller 使用
`fail-fast: false`，因此每个 row
形成独立动态 child 与 evidence；这些 child 只恢复共享 Rust cache，不作为 required checks。target taxonomy、
资源需求与本地故障定位见
[`202607111214-1730-integration-shards.md`](./202607111214-1730-integration-shards.md)。

Core tests 的两个 partition 使用相同 workflow lane/tool-cache profile key，因此 protected `develop` push
仅指定 `1/2` 为 writer，`2/2` 恒只读；其它当前 workflow tool-cache profile 各有单一 writer 资格。该闭集由
`CI-CACHE-WRITER-01` 的 reusable workflow guard 精确锁定，避免同 key save race。
