# #1733 CI SLO 预算与排障

CI SLO 的规则单源是 `.config/ci-slo.toml` schema v2，执行载体是
`cargo xtask ci-slo evaluate` 与 reusable workflow `.github/workflows/rss-rust-lane.yml`。本文只说明
carrier 的运维语义；约束和 gate 以机器载体上的 `INVARIANT` 为准。

## 预算与判定

`[limits]` 对全部闭合 job 共用：可用磁盘下限为 5 GiB，target、download cache、tool cache 和 staged
artifact 上限依次为 6、8、2、1 GiB。`[[duration_budgets]]` 精确覆盖配置中的 15 个 typed job；未知、
重复或遗漏 job 都会使配置失效。

评估口径固定如下：

- duration：`start` 到 `after-save` 的完整生命周期时长；
- disk-free：五个 snapshot 的最小 `filesystem.availableBytes`，即磁盘低水位；
- target：五个 snapshot 中 job-local target 的最大体积；
- download-cache、tool-cache：各自 restored footprint 与 candidate size 的最大值；
- artifact：`target/job-evidence` staging tree 内普通文件的字节总和，不是上传后的压缩量。

compiler cache 的 requests/hits/misses/non-cacheable、六类 errors 和 `resourceUsage` 用于诊断，不设置
独立数值阈值。任一 compiler cache error 非零会把整体判定至少提升为 `WARN`，summary 标记
`DEGRADED` 并输出固定分类计数，workflow annotation 同步告警；它仍退出 0，且不会覆盖原有 build/test
结果。恰好等于预算阈值算通过。duration、target、两类持久化 cache 或 artifact 超限产生 `WARN`，退出
0；disk-free 低于 5 GiB 产生 `FAIL`，非零退出。配置错误、证据错误、identity 不匹配、非法路径或无法
测量属于 operational error，同样 fail-closed。annotation 只含闭合 metric/错误分类、整数值与固定 unit，
不回显证据内容。

## Workflow 生命周期与 artifact

`.github/scripts/ci-disk-budget.sh` 是构建过程中的 live hard guard；Rust evaluator 是 staged evidence
形成后的 post-hoc 判定和 Job Summary，不替代在线门。两者从当前 checkout 的固定配置读取同一阈值，
shell 不接受 override。

尾部顺序固定为 `after-save → Stage job evidence → Upload CI evidence → Evaluate CI SLO / write summary`。
artifact pointer 由 typed job 与 run identity 重建：
`ci-evidence-<lane>-<shard-or-workspace>-<partition-label>-<run-id>-<run-attempt>`，未分区 label 为
`unpartitioned`，保留 7 天。上传失败、取消或跳过时 pointer 为 `unavailable`，不得伪造可下载名称。

Stage、Upload 和 Evaluate 使用 `always()` 保存普通失败/取消路径，但无法覆盖 checkout 前失败、runner
失联、强制终止或平台未调度 step。

## 严格输入与安全边界

evaluator 只接受 config schema v2 与 CI evidence schema v4。证据必须恰好包含五个有序 snapshot、合法且
单调的 UTC RFC 3339 时间、闭合枚举、JSON 安全整数和与 CLI 一致的 run identity。compiler cache 启用时
必须是 `sccache 0.15.0` 与闭合 access；hits + misses 不得大于 requests。`compilerCache.errors` 必须恰好
包含 `restore`、`stats`、`cacheIo`、`noRequests`、`measure`、`save` 六个 JSON 安全非负整数；旧标量形状、
遗漏分类和额外分类均直接拒绝。

配置与证据必须是固定路径上的普通文件；staging tree 只允许闭合顶层布局、受限深度/数量的 UTF-8 名称、
普通目录与普通文件。symlink、FIFO、越界层级、数值溢出和未知字段均 fail-closed。summary 只渲染 typed
job、固定 metric、整数值与 verdict；任意证据文本、原始路径和 HTML 不进入 summary。

## 本地复现

在对应 revision 上下载并解包同一 artifact，然后准备 evaluator 的固定 staging path：

```bash
cd <matching-revision-worktree>
rm -rf target/job-evidence
mkdir -p target/job-evidence
cp -R <artifact-download-dir>/. target/job-evidence/
test -f target/job-evidence/ci/ci-evidence.json

cargo xtask ci-slo evaluate \
  --lane ci-meta \
  --run-id <run-id> \
  --run-attempt <run-attempt> \
  --upload-outcome success

cargo xtask ci-slo evaluate \
  --lane integration \
  --shard event-transport \
  --partition 1/2 \
  --run-id <run-id> \
  --run-attempt <run-attempt> \
  --upload-outcome success
```

`.config/ci-slo.toml`、`target/job-evidence/ci/ci-evidence.json` 与 staging tree 必须来自同一 revision/run。
复现 upload failure 时将 `--upload-outcome` 改为真实 outcome；该参数只控制 pointer，不放宽证据校验。
`--github-summary` 只供 workflow 使用，本地不要设置。

## 排障顺序

1. 区分 live disk guard、Stage、Upload、Evaluate 与 runner/platform 中断。
2. 按 summary pointer 下载同一 run/attempt artifact；`unavailable` 时先查 Upload step。
3. 验证 config schema v2、evidence schema v4、typed job、source/plan identity、五阶段、时间和 staging tree 闭合布局。
4. 按 metric 定位：disk-free 看低水位，target 看 job-local 最大值，download/tool 看 restore/candidate，
   artifact 看 staging 普通文件，duration 看首尾时间。
5. compiler cache 收益另看 summary 中的 requests/hits/misses/non-cacheable 与 CPU/peak RSS；再按
   restore/stats/cache-io/no-requests/measure/save 分类定位降级阶段。backend errors 只应降低性能，不得改变
   build/test verdict。
6. `WARN` 表示预算漂移或 compiler cache 降级；非零退出必须处理 disk critical 或 operational error，不能
   通过改 outcome、删 evidence 或绕过 hard guard 消除。
