# #1733 CI SLO 预算与排障

CI SLO 的规则单源是 `.config/ci-slo.toml` schema v1，执行载体是
`cargo xtask ci-slo evaluate` 与 reusable workflow `.github/workflows/rss-rust-lane.yml`。本文只说明这些
carrier 的运维语义；约束强度、证明和 gate 以 carrier 上的 `INVARIANT` 锚点为准，不在文档中维护另一份规则清单。

## 预算与判定

`[limits]` 对全部闭合 job 共用：可用磁盘下限为 5 GiB，target、build cache、tool cache 和 staged artifact
上限依次为 6、8、2、1 GiB。`[[duration_budgets]]` 必须精确覆盖 14 个 typed job：`ci-meta` 为 90 秒；
`ci-core-prerequisites` 与两个 `ci-core-tests` partition 各为 600 秒；`ci-security` 和 `audit` 各为
300 秒；`ci-coverage` 为 480 秒；七个 Integration shard/partition job 各为 900 秒。完整 job key 及其
唯一预算以配置文件为准，未知、重复或遗漏项都会使配置失效。

评估口径固定如下：

- duration 是 `start` 到 `after-save` 的完整生命周期时长。
- disk 是 `start`、`after-cache`、`after-build`、`before-save`、`after-save` 五个 snapshot 的最小
  `availableBytes`。
- target 是五个 snapshot 中 target 目录的最大体积。
- build cache 与 tool cache 分别取自身 restored footprint 和 candidate size 的最大值，再跨 snapshot 取最大值。
- artifact 是 `target/job-evidence` staging tree 内普通文件的字节总和，不是 GitHub 上传后的网络压缩量。

恰好等于阈值算通过。duration、target、两类 cache 或 artifact 超限产生 `WARN`，命令退出 0；disk 低于
5 GiB 产生 `FAIL`，命令非零退出。配置错误、证据错误、run identity 不匹配、非法路径或无法完成测量属于
operational error，同样 fail-closed 并非零退出。每个 `WARN` 还会向 GitHub runner 的 stderr 发出只含闭合
metric、整数 actual/budget 和固定 unit 的 warning annotation；不会回显证据内容，也不改变退出码。

## Workflow 生命周期与 artifact

`.github/scripts/ci-disk-budget.sh` 是执行过程中的 5 GiB live hard guard：在关键阶段立即阻止低磁盘 job
继续消耗 runner。Rust evaluator 是 staged evidence 已形成后的统一 post-hoc 判定与 Job Summary，不替代在线硬门；
两者都从 workspace 固定路径 `.config/ci-slo.toml` 读取同一阈值，shell 不接受阈值 override。

尾部顺序固定为 `after-save → Stage job evidence → Upload CI evidence → Evaluate CI SLO / write summary`。
Stage 先把证据收敛到 `target/job-evidence`，Upload 再上传，因此 evaluator 发生 critical 或 operational failure
时仍可用已上传 evidence 排障。上传成功时，summary 中的 pointer 由 typed job 与 run identity 独立重建，格式为
`ci-evidence-<lane>-<shard-or-workspace>-<partition-label>-<run-id>-<run-attempt>`；未分区 label 为
`unpartitioned`。artifact 保留 7 天。上传失败、取消或跳过时，pointer 明确显示 `unavailable`，不得伪造一个
可下载名称。

Stage、Upload 和 Evaluate 都使用 `always()`，用于保留正常失败或取消路径的证据与总结。但 `always()` 无法覆盖
checkout 前失败、runner 失联或被强制终止、以及平台未调度 step 的情形；这些情况应结合 GitHub run/runner
状态判断，不能解释为 evaluator 通过。

## 严格输入与安全边界

evaluator 只接受 config v1 与 CI evidence v2。证据必须恰好包含上述五个有序 snapshot、合法且单调的 UTC
RFC 3339 时间、闭合枚举、JSON 安全整数和与 CLI 一致的 run ID/attempt。配置与证据文件必须是固定路径上的
普通文件；staging tree 只允许闭合顶层布局、受限深度和数量的 UTF-8 名称、普通目录与普通文件。symlink、FIFO
等特殊文件、越界层级、超量文件、数值溢出或任意未知字段都会 fail-closed。summary 只渲染 typed job、固定
metric、整数值和 verdict，不回显任意证据文本、原始路径或 HTML。Operational summary 只显示闭合的
identity/config/evidence/artifact code、category 和固定恢复动作；原始错误链只保留在 step stderr。

## 本地复现

先在与该 run 对应的 revision 上下载并解包 artifact，然后准备 evaluator 使用的固定 staging paths。不要把
下载目录本身作为 CLI 参数；CLI 不接受任意 config/evidence/artifact 路径。

```bash
cd <matching-revision-worktree>
rm -rf target/job-evidence
mkdir -p target/job-evidence
cp -R <artifact-download-dir>/. target/job-evidence/
test -f target/job-evidence/ci/ci-evidence.json

# 非分区 CI lane 示例
cargo xtask ci-slo evaluate \
  --lane ci-meta \
  --run-id <run-id> \
  --run-attempt <run-attempt> \
  --upload-outcome success

# 分区 Integration 示例；CLI partition 使用 M/N，而 artifact label 使用 M-of-N
cargo xtask ci-slo evaluate \
  --lane integration \
  --shard event-transport \
  --partition 1/2 \
  --run-id <run-id> \
  --run-attempt <run-attempt> \
  --upload-outcome success
```

`.config/ci-slo.toml` 必须来自当前 checkout；`target/job-evidence/ci/ci-evidence.json` 与 staging tree 必须来自
同一个 artifact，且 run ID/attempt 要与证据一致。若正在复现 upload failure，应保留本地 staged 内容并把
`--upload-outcome` 改为真实的 `failure`、`cancelled` 或 `skipped`；该参数只控制 summary pointer，不放宽证据校验。
`--github-summary` 只供 reusable workflow 使用：warning workflow command 写 stdout，Markdown 直接追加到 runner
提供的 `GITHUB_STEP_SUMMARY`；本地复现不要设置该开关。

## 排障顺序

1. 先看 step 拓扑和结论，区分 live disk hard guard、Stage、Upload、Evaluate，以及 runner/platform 级中断。
2. 若上传成功，按 summary 名称下载同一 run ID/attempt 的 7 天 evidence artifact；pointer 为 `unavailable` 时先查
   Upload step，不能据名称猜测 artifact 存在。
3. 检查 `ci/ci-evidence.json` 是否为 schema v2、五阶段齐全有序、时间单调、identity 匹配；再检查 staging tree
   是否含 symlink、特殊文件或闭合布局之外的条目。
4. 按 summary 的 metric 定位：disk 查看五阶段最小值，target 查看五阶段最大值，两类 cache 查看
   restore/candidate 最大值，artifact 查看 staging 普通文件总量，duration 查看首尾时间。
5. 在对应 revision 按上述固定路径和原 run identity 本地重跑。`WARN` 只表示预算漂移；非零退出必须先处理
   disk critical 或 operational error，不能通过修改 outcome、删证据或绕过 hard guard 消除。
