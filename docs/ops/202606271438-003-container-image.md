# RSS 容器镜像与运行契约

> #1134（area-tooling）。本文档是 `bins/server` 多阶段 Dockerfile + 最小运行镜像的构建 / 运行 / 验收 /
> 编排契约。镜像构建逻辑单源 = 仓库根 `Dockerfile`；演示栈 = `deploy/docker-compose.yml`；冒烟 acceptance
> harness = `deploy/smoke.sh`（`make docker-smoke`）。Serving 配置单源 = `assemblies/runtime/src/config.rs`
> 的 closed `RuntimeConfigSnapshot` catalog 与唯一 `RuntimeServingConfig::from_snapshot` typed mapping；
> projection、audit、DLQ、reconcile 四个逐名且要求 operator-only capability 的 maintenance grant reader
> 是 serving catalog 外的具名例外。

## 背景

RSS 此前没有 Dockerfile 或 Compose 容器载体。本文档随第一份容器化交付单元落地：把
`bins/server`（薄入口 → `runtime::run()`）编进**非 root、只读 rootfs 友好、distroless** 的最小运行镜像，
并给出可机器闭环验收的演示栈（`docker run → /readyz 200`；默认 all-Local 必须七闭环；
仅 Remote placement 才需要 SPIFFE/SPIRE fixture）。fixture 不全默认失败；只有显式 developer opt-in
可以输出 `NOT PRODUCTION EVIDENCE` 并跳过，release 永不跳过。

> **scaffold 阶段声明**：当前 runtime compose `SettingsDomain` + `IdentityDomain` + `AuditDomain`。对外**匿名可验收面**是
> `/health/v1/*`（healthz/readyz/**metrics**，Health listener 8083，`AuthScheme::NoAuth`）以及 Primary 上的
> identity login（Public opt-out）；其余 identity / settings / audit 管理面挂 Primary/Admin listener，按 listener 鉴权保护。
>
> **匿名 metrics 面的网络边界（运行契约，非仅代码约定）**：`/health/v1/metrics` 与 healthz/readyz 同挂
> `NoAuth` Health listener（`diport::MetricsExporter` 规约要求 scrape 面仅内部网络可达）——**必须仅 loopback /
> cluster-internal 暴露，绝不作公网 ingress 入口**。演示栈已在 `deploy/docker-compose.yml` 把 8083 绑 `127.0.0.1`
> 落实该边界；生产 delivery 系统必须提供等价的受控内部网络与 scrape 边界（见 §可观测性导出）。
> 镜像真实启动、连 PG、跑迁移、serve readyz 是容器化交付链的验收目标；默认 all-Local 必须七闭环。
> Remote placement 且 SPIFFE fixture 不全时，只有
> `RSS_SMOKE_MODE=developer RSS_SMOKE_ALLOW_SKIP=1` 可以跳过并输出唯一
> `NOT PRODUCTION EVIDENCE`；release 模式失败。业务端点随后续域 PR 进入同一镜像，Dockerfile 不变。

## 镜像结构（多阶段 cargo-chef + distroless）

`Dockerfile` 4 阶段（ref: cargo-chef README.md / ref: distroless examples/rust/Dockerfile）：

| 阶段 | 基底 | 职责 |
|------|------|------|
| `chef` | `rust:1.96.0-bookworm` | 钉版工具链（= `rust-toolchain.toml` channel）+ `cargo-chef`（钉 0.1.77；须 ≥0.1.71 支持 edition 2024）。 |
| `planner` | `chef` | `cargo chef prepare` → `recipe.json`（仅依赖图，**不含业务源** ⇒ 改代码不失效）。 |
| `builder` | `chef` | 只构建 serving `server` 二进制。 |
| `operator-builder` | `chef` | 只构建 migration/maintenance `rss` 二进制。 |
| `runtime` | `gcr.io/distroless/cc-debian12:nonroot` | 只包含 `/usr/local/bin/server`；非 root uid 65532；无 shell / 包管理器。 |
| `operator-runtime` | `gcr.io/distroless/cc-debian12:nonroot` | 只包含 `/usr/local/bin/rss`，不承载 serving listener。 |

**为什么 distroless/cc**：server 二进制 glibc 动态链接、TLS 走 rustls+ring（ring 静态、**无 OpenSSL/
native-tls 动态依赖**），运行期只需 glibc + libgcc + ca-certificates——`cc-debian12` 恰好提供，再无多余攻击面。

## 构建

```bash
docker build --target runtime -t rss-runtime:dev \
  --build-arg GIT_SHA="$(git rev-parse HEAD)" \
  --build-arg BUILD_DATE="$(date -u +%Y-%m-%dT%H:%M:%SZ)" .
docker build --target operator-runtime -t rss-operator:dev .
```

`.dockerignore` 把上下文裁到「cargo 解析整个 workspace + 编 `--bin server` 子图」所需的最小集（排除
`target/`、`lints/`〔独立 workspace〕、`contracts/`〔仅 xtask codegen 输入，无 build.rs 消费〕、docs/ 等）。
构建期须通过 `GIT_SHA` / `BUILD_DATE` ARG（→ ENV → `bins/server/build.rs`）烘焙二进制身份；镜像内无 `.git`，
且 Dockerfile **不设 ARG 默认值**——缺参 / `unknown` / 非法格式在 `cargo build` 前 fail-closed。
`server version` 输出两行 `GIT_SHA=` / `BUILD_DATE=`；`deploy/smoke.sh` 经 `deploy/server-version-identity.sh`
共享 seam 离线校验发布产物一致性（#1496）。

## 运行：必填环境变量

server 对**缺失的必填变量 fail-fast**（启动即 `Err` 退出、错误含变量名，不静默 noop）。完整演示值见
`deploy/.env.example`。

### Listener 明文策略

HTTP listener 明文 bind 默认 fail-closed。`RSS_LISTENER_ALLOW_PLAINTEXT=true` 仅用于本机 dev/test，只允许
`127.0.0.1` / `::1` loopback bind；`RSS_LISTENER_ALLOW_PLAINTEXT=dev-container` 只用于 compose 演示栈，额外允许
`0.0.0.0` / `[::]` wildcard bind 供端口映射使用，仍拒绝固定非 loopback 地址。Primary / Admin / Health listener
以及 Internal `service-token` 本机测试路径都属于 plaintext listener；显式选择 `mtls` 的 Internal 由 SPIFFE/rustls listener
承载，不受明文 opt-in 门约束。

> #1710 / #1649 边界：egress（AMQP / Redis / S3 / PG）已禁止一切 `*_ALLOW_PLAINTEXT` 与 `RSS_PG_SSL_MODE`；
> **仅** ingress listener 仍保留 `RSS_LISTENER_ALLOW_PLAINTEXT=dev-container` 供 compose 端口映射。

Internal `service-token` 只保留为 loopback 本机测试路径。若绑定到 `0.0.0.0` / `[::]` 或固定非 loopback 地址，
启动直接 fail-fast；旧 `RSS_INTERNAL_SERVICE_TOKEN_MIGRATION_*` env 不再放行非 loopback 绑定。生产 Internal listener
必须使用 SPIFFE/mTLS。

### Profile-specific JWKS 文件源

RSS Access 与 Federated Access 各自只从其 profile namespace 指向的本地 JWKS 读取，绝不共享 provider、keyset
或 readiness。文件在启动期必须存在、可读且只含有非空唯一 `kid` 的 P-256 ES256 key（初始加载失败
fail-fast，不可降级启动）；Service Token 不读 JWKS，只使用其 HS256 namespace。刷新失败不换出空
keyset，继续保留 last-good，并把对应 `rss_access_token_jwks_ready` /
`federated_access_token_jwks_ready` 标为 **Degraded**（`/readyz` 聚合仍 200，不摘流量）。

生产应由外部 delivery agent 或受控文件投影负责把每个 IdP/Vault Transit public key 输出到该 profile
独占路径，并用原子 rename/投影更新。RSS Access `export-vault-transit` 须合并 **Active + Retiring（及可选
Next）** 写入 `RSS_ACCESS_TOKEN_JWKS_PATH`；配置了 Retiring 时禁止单 key / 只写 Active 的整文件覆盖。
compose demo 用 `rss-access-jwks-init` 调用 `rss rss-access-jwks export-vault-transit`（demo 栈仅 Active，
无 Retiring）；生产轮换见 [Security Production Closeout](./security-production-closeout.md#rss-access-signing-key-rotation)。

### Token profile 破坏式发布

Token profile 发布必须按
[Security Production Closeout 的 Atomic Token Profile Cutover](./security-production-closeout.md#atomic-token-profile-cutover)
执行。禁止新旧 binary 共处同一 serving pool 或共享流量；先停止旧 generation 与登录/refresh，使用经审计的
DB owner 维护事务撤销全部 active refresh token 和 active AuthGrant，再按最长 profile lifetime 排空完整
900 秒。随后把 binary、listener selectors、profile namespaces、JWKS/key bundle 作为一个密封单元切换，
readiness 全绿后才恢复流量，并要求所有用户、设备与 operator 重新认证。回滚同样整体切 binary + config/key
bundle，切换前再次撤销新 generation 产生的 refresh/AuthGrant；不得通过 alias、双读或混池回滚。

#### Full runtime production generation

Full runtime 的 production 发布同样不承诺旧/新 generation 混跑。迁移 0072/0073 的发布先停止旧
generation、禁用自动重启、记录静态 PostgreSQL lane 与 migration ledger 证据。随后只允许
待发布 operator 镜像的 migration task 使用 migration capability 执行 `rss postgres migrate-all`；任务必须完成且
`_sqlx_migrations` ledger 精确等于该镜像 HEAD，才允许同 generation 的两个 serving 副本进入流量池。serving
副本只读核验 ledger，不能执行 migration；stale、超前或分叉 ledger 均 fail closed。

新 generation 内允许逐副本 drain/replacement：摘流后发送 SIGTERM，存活副本必须在整个 drain 窗口维持完整
readiness 与关键 worker probes，退出副本必须完成 runtimeexec resource drain。该证据不表示分布式 leader 协议发生
转移，也不放宽 0072/0073 的 forward-only rollback fence。精确验收与 provider outage 边界见
[Runtime Production Acceptance](./runtime-production-acceptance.md)。

### Vault tenant/store allowlist 发布与故障语义

`RSS_VAULT_TENANT_STORE_ALLOWLIST_JSON` 与消费它的 binary 是一个不可拆分的发布单元。先用同版本 binary
离线校验唯一受支持的 `{"bindings":[...]}` 形态，再以同一次 Secret/ConfigMap generation 原子发布 binary 与配置：

```bash
rss vault-allowlist validate --file /run/rss-config/vault-allowlist.json
# 或严格从 stdin 读取；不接受 env/flag 内联 JSON 等其他来源
rss vault-allowlist validate --stdin < /run/rss-config/vault-allowlist.json
```

该命令在 runtime 配置快照和 provider 构造前完成，不要求 Vault 地址/token/CA，不访问网络；成功只输出
`vault allowlist validation succeeded`，失败只输出闭合静态分类，不回显文件路径或输入内容。不得先发布
会要求该变量的新 binary，也不得先向旧 binary 投放新语义。每条 binding 必须唯一标识
`(tenantId, storeId)`，且不同租户不得映射到相同或祖先/后代重叠的 Vault 物理命名空间。

- allowlist 缺失、空、JSON/字段/UUID/路径非法、重复或跨租户重叠属于**配置无效**：进程在监听端口前
  fail-fast，不进入 readiness 降级模式。
- 合法但未授权的 `(tenantId, storeId)` 属于**请求级 Forbidden**：resolver 在发出 Vault 网络请求前拒绝，
  不写入任何 readiness 状态。
- Vault KV mount/ACL/canary 不可达属于**resolver provider down**：独立 sampler 把
  `vault_secret_resolver_ready` 标成 unhealthy，使 `/readyz` 返回 503；Transit-only
  `keyprovider_ready` 可以继续 healthy。不得把 provider down 伪装成 Forbidden。

回滚只允许恢复精确的上一版 binary + allowlist/config bundle，二者完成 readiness 后再恢复流量。该变更不改
数据库 schema、持久化数据或密文格式，因此不执行数据库/持久化回滚，也不得增加变量 alias、双读或 fallback。

### Outbound Domain Transport mTLS

跨域同步 HTTP transport 只支持 SPIFFE/mTLS。Remote placement（`RSS_<DOMAIN>_DOMAIN_PLACEMENT_WORKLOAD`
异于本 assembly identity）的每个 domain 都会在启动期构造一个 HTTPS endpoint + SPIFFE mTLS reqwest client；缺 endpoint、缺
`RSS_<DOMAIN>_DOMAIN_TRANSPORT_MTLS_SPIFFE_ALLOW_SET`、SPIRE source 不可用、当前 SVID 与
`RSS_DOMAIN_TRANSPORT_MTLS_LOCAL_SPIFFE_ID` 不一致、rustls/reqwest client 构造失败均 fail-fast。
全部 Local 时走 InProc stub（dispatch fail-closed，`domain_transport_ready=ready`）。runtime 同时注册
`domain_transport_ready` 探针；它只表示本进程持有可用且未过期的 outbound SPIFFE material，运行期
每次 readiness 采样与每次 outbound dispatch 都会把当前 SVID 与配置的 local SPIFFE ID 做 exact equality；source 关闭、supervisor 停止、
无可选 SVID、SVID 过期或轮换到非预期 ID 时会使 `/readyz` 聚合为 503，并在创建任何目标网络 attempt 前拒绝 dispatch。该探针不执行 peer
DNS/TCP/TLS/HTTP 主动探测；peer 失败仅由 dispatch error/timeout metric 与 trace 呈现，不触发本进程摘流。
`bootstrap::domaintransport` 只做 topology/URL resolver；mTLS policy 在 runtime 组合根构造。

### PG TLS（始终 VerifyFull）

PG 连接 TLS **固定** `VerifyFull`（强制 TLS + 校验证书链 / 主机名，零信任）。`RSS_PG_SSL_MODE` 已禁止
（#1710：出现即启动 fail-fast）。`RSS_PG_SSL_ROOT_CERT_PATH` 必填：空值、不可读路径或目录路径都会在
配置构造期 fail-fast。演示栈由 `deploy/demo-tls/generate-demo-cas.sh` 生成 trust-anchor PEM + leaf，compose 挂载到
`/run/rss-demo-tls/postgres/ca.pem`；生产注入真实 trust-anchor（私有 CA 或组织根均可）。

宿主 `psql` 连演示栈须显式 SSL（compose 已启 `ssl=on` + `hostssl`）：

```bash
export PGSSLMODE=verify-full
export PGSSLROOTCERT=deploy/demo-tls/out/postgres/ca.pem
psql -h 127.0.0.1 -p 5432 -U rss_app -d rss
```

### LocalOnly reader 凭据发布与轮换

`0067` 负责创建或收敛 `rss_app_read` 的属性与 ACL，但不在 migration 中固化密码。存量数据库发布必须按
“先 migration、后凭据、再 binary”的顺序执行：

1. 用待发布 operator 镜像的显式 migration task 将 schema 从当前 ledger forward-only 升级到 HEAD；该入口只读取 migrator
   凭据，不构造 serving/reader pool，也不要求 reader 密码：

   ```bash
   docker run --rm --entrypoint /usr/local/bin/rss \
     --env-file <non-secret-env-file> \
     --mount type=bind,src=<database-url-file>,dst=/run/secrets/pg-migration-database-url,readonly \
     <operator-image> postgres migrate-all
   ```

   env file 只含非 Secret 配置与 `RSS_PG_DATABASE_URL_FILE=/run/secrets/pg-migration-database-url`；
   密管以 `0400` 只读文件挂载包含口令与 `sslmode=verify-full` 的 DSN。任务使用 SQLx advisory lock、checksum 与 ledger，并在结束时核验精确 HEAD。
2. 在密管中生成高强度密码，以绝对只读文件挂载 migrator 与 reader 口令后运行
   `deploy/postgres-upgrade/provision-reader-role.sh`。脚本读取文件后通过 psql `\getenv` 传递 reader 密码，不把秘密写入
   migration、命令行参数、DSN 或日志，并拒绝 role membership / ownership 漂移。
3. 用同一密管版本填充 `RSS_PG_READ_USERNAME=rss_app_read` 与 `RSS_PG_READ_PASSWORD_FILE`，完成下述直连预检后再发布
   新 binary。任一 reader 配置或能力门失败都应阻断放量。

密码轮换使用“密管 staged version → PostgreSQL 改密码 → 立即 promote staged version → 滚动重启”。PostgreSQL 修改
密码不会中断已建立的 reader 连接，但旧密码在过渡窗口无法建新连接；因此必须监看双 pool readiness，并在
新版本预检通过后立即完成滚动。若需回滚，回滚 binary 的同时也要将 workload secret 指回与数据库当前密码
一致的密管版本；不得让 runtime 回退使用 writer 凭据。

下列操作从 TTY 静默读入凭据，`psql` 只输出角色、默认只读、固定 search path 与 LO 兼容模式状态，不回显密码。执行前必须关闭 `set -x`，
并用独立的 `PGHOST` / `PGPORT` / `PGDATABASE` 变量，不得将凭据拼进 URL：

```bash
# 由具有 ALTER ROLE 权限的 psql 会话执行；\prompt -s 不回显输入。
psql -X --set=ON_ERROR_STOP=1 <<'SQL'
\prompt -s 'new rss_app_read password: ' reader_password
ALTER ROLE rss_app_read PASSWORD :'reader_password';
\unset reader_password
SQL

# 密管将待发布版本写入 RSS_PG_READ_PASSWORD_FILE 指向的 0400 文件。
# 演示/TLS 栈还须设置 PGSSLMODE=verify-full 与 PGSSLROOTCERT=<trust-anchor.pem>。
PGPASSWORD="$(<"$RSS_PG_READ_PASSWORD_FILE")" \
PGSSLMODE="${PGSSLMODE:-verify-full}" \
PGSSLROOTCERT="${PGSSLROOTCERT:?set trust-anchor PEM path}" \
psql -X --no-password \
  --host "$PGHOST" --port "$PGPORT" --dbname "$PGDATABASE" --username rss_app_read \
  --tuples-only --no-align \
  --command "SELECT session_user, current_setting('transaction_read_only'), current_setting('search_path'), current_setting('lo_compat_privileges');"
unset PGPASSWORD
# 期望唯一输出：rss_app_read|on|pg_catalog, public|off
```

保留数据卷的升级演练使用 `make postgres-reader-upgrade-smoke`：predecessor-only 集成 harness 先通过
SQLx `Migrator` 在同一 PG16 volume 建立真实 `0001..0066` ledger/checksum/lock 状态并写入 marker；随后
执行当前待发布源码构建出的 `rss postgres migrate-all`，再运行正式 provisioning 脚本。演练最终
核验 0067 ledger/checksum、旧数据仍在、历史 column ACL 已收敛和 reader 默认只读。容器启动等待有 90 秒
截止时间，并在提前退出或超时时输出有界日志后失败。

### Legacy ConfigValue 明文门

`config_entries.protection_scheme=0` 代表加密迁移前的 legacy plaintext `ConfigValue` 行。runtime 在
`run_migrations` 后、serving pool 建立前用 migrator 连接扫描全库；默认发现任意行即 fail-fast，避免生产在
未评估明文存量时继续对外服务。`RSS_SETTINGS_ALLOW_LEGACY_PLAINTEXT_CONFIG_VALUES=true` 只作为 backfill 前的
短期人工豁免；新写路径仍只写 encrypted scheme，serving 读路径也不再返回 scheme=0 plaintext。

存量迁移使用 `operator-runtime` 镜像内 `/usr/local/bin/rss` 命令。serving `runtime`
镜像只包含 `/usr/local/bin/server`，禁止在 serving 容器中 exec operator：

```bash
docker run --rm -i <operator-image> \
  settings-config-values maintenance --operator-service-token-stdin --operator-tenant <uuid> \
  --operation both --dry-run --batch-size 500 < /run/secrets/rss-operator-service-token
```

可用 `--tenant <uuid>` 分租户执行，用 `--max-rows <n>` 控制整条命令的单次处理量；`--operation both` 下该预算由
backfill 与 rewrap 共享。每次运行必须通过 `--operator-service-token-stdin` 从标准输入提供可验签 token，并带其
`--operator-tenant <uuid>` exact-one challenger（须与 token signed `tenant_id` equality）；命令从已验证 service principal 派生 audit subject，并写 job start/finish
durable audit。只有无 `--tenant` 的全局验证命令输出 `failed=0` 且 `remaining_plaintext=0` 后，才移除
`RSS_SETTINGS_ALLOW_LEGACY_PLAINTEXT_CONFIG_VALUES`。

Vault `min_decryption_version` 收紧不是 `remaining_plaintext=0` 的直接后续步骤：它还要求按 key rotation runbook
完成无限量 rewrap 覆盖验证，不能用带 `--max-rows` 的批次结果作为禁旧版本依据。

### S3 Object Store Canary

runtime 不再把 S3 保留为未来接线：`run()` 启动期必填 S3 env，构造 `S3RuntimeDeps`，并注册
`s3_object_store_ready` readiness probe。canary worker 启动后立即执行一轮真实对象操作，之后按
`RSS_S3_CANARY_INTERVAL_SECS` 周期重复；任一轮 put/get/delete/get-miss 失败或超时，readyz 聚合为 503。

生产 endpoint 必须是 `https://`，HTTP client 由 runtime 用 `aws-smithy-http-client` 显式选择 rustls+ring，
并经 `RSS_S3_CA_CERT_PEM_PATH` 注入私有 CA（#1710）。`RSS_S3_ALLOW_PLAINTEXT` 已禁止——出现即启动
fail-fast；不得用 `http://`。S3 endpoint URL 不允许 userinfo、query、fragment，避免凭据或 token 出现在
URL 与诊断面。演示栈 MinIO 启 TLS（`--certs-dir`），endpoint 为 `https://minio:9000`。

## 演示栈与闭环验收

```bash
bash deploy/demo-tls/generate-demo-cas.sh   # 生成 egress 私有 CA + leaf（smoke.sh 会自动跑）
make docker-smoke            # 显式 developer；默认禁止 skip，all-Local 必须完成全部闭环
RSS_SMOKE_MODE=release ./deploy/smoke.sh # release image 在 demo infra 上的完整闭环
# 或手动（server 镜像构建必填 GIT_SHA / BUILD_DATE；缺省 compose 以 `:?` fail-closed）：
export GIT_SHA="$(git rev-parse HEAD)"
export BUILD_DATE="$(date -u +%Y-%m-%dT%H:%M:%SZ)"
docker compose -f deploy/docker-compose.yml up --build -d
curl -fsS http://localhost:8083/health/v1/readyz   # all-Local → 200, {"overall":"healthy", ...}
curl -fsS http://localhost:8083/health/v1/healthz  # → 200（liveness 恒 200）
curl -fsS http://localhost:8083/health/v1/metrics  # → 200, content-type text/plain; version=0.0.4（Prometheus exposition）
docker compose -f deploy/docker-compose.yml down -v
```

一致性运维入口见 `docs/runbooks/202607082104-1642-consistency-ops-runbook-index.md`；dashboard 面板清单见
`docs/ops/202607082104-1642-consistency-dashboard-checklist.md`。上面的 metrics smoke 只证明 Prometheus
exposition 端点可抓取，不代表每个 consistency 模块都有 server runtime metric；inbox backlog 与 projection
runtime metrics 当前分别由 #1683 / #1684 跟踪，operator-local / journey-local metric 见 checklist omission 表。

`make docker-smoke` 为避免本机常见 8080 端口冲突，会默认导出 host 端口
`RSS_PRIMARY_HOST_PORT=18080`、`RSS_INTERNAL_HOST_PORT=18081`、`RSS_ADMIN_HOST_PORT=18082`、
`RSS_HEALTH_HOST_PORT=18083`；手动 compose 未设置这些变量时仍使用 8080-8083。

#1649 补齐 SPIRE Server/Agent、Workload API socket mount、registration entry 与 domain transport allow-set 前，
`deploy/smoke.sh` 会在 preflight 检测到**已配置 Remote placement**（`RSS_*_DOMAIN_PLACEMENT_WORKLOAD`
异于 assembly identity）且缺 `SPIFFE_ENDPOINT_SOCKET` 或 `RSS_DOMAIN_TRANSPORT_MTLS_LOCAL_SPIFFE_ID`
时默认失败。只有 `developer + RSS_SMOKE_ALLOW_SKIP=1` 会列出缺失变量、输出
`NOT PRODUCTION EVIDENCE` 后成功终止；release 禁止 skip 与 `KEEP_UP=1`。release 完整成功输出
`RELEASE IMAGE ON DEMO INFRA EVIDENCE`，只证明 release image 在此 demo compose 上完成精确
probe down/up 与整体 readiness 闭环，不证明生产 secret manager 配置或正式基础设施（演示栈 egress 已启
TLS，但仍是 demo 私有 CA，非生产身份/编排）。全部 Local
时不把可选 placement workload 当作 SPIFFE fixture 门。`SPIFFE_ENDPOINT_SOCKET` 对 Internal inbound
mTLS 或任何 outbound domain transport 条件必填；两条路径都只消费同一进程快照并显式传入 endpoint。

compose 会启动 `hashicorp/vault` 的 `-dev-tls` 模式，`vault-init` 初始化 `transit` mount、KV v2 `secret`
mount 及 `tenants/a/.rss-readiness` canary，随后初始化
`RSS_SETTINGS_CONFIG_VALUE_KEY_NAME` 对应 `derived=true` key 和 `RSS_ACCESS_TOKEN_SIGNING_ACTIVE_KEY_ID` 签名 key。`rss-access-jwks-init`
随后从该签名 key 的 current public key 生成 `RSS_ACCESS_TOKEN_JWKS_PATH` 指向的 JWKS。生成的 `vault-ca.pem` 与
JWKS 分别通过只读 volume 挂给 server。生产不得使用 dev-tls；生产 JWKS 应由正式 IdP/Vault export agent 管理。

生产 runtime Vault token 至少需要允许 settings ConfigValue key 执行 encrypt/decrypt/rewrap，并允许
`RSS_ACCESS_TOKEN_SIGNING_ACTIVE_KEY_ID` 对应的 RSS Access signing key 执行 sign：

```hcl
path "transit/encrypt/<settings-config-key>" { capabilities = ["update"] }
path "transit/decrypt/<settings-config-key>" { capabilities = ["update"] }
path "transit/rewrap/<settings-config-key>"  { capabilities = ["update"] }
path "transit/sign/<jwt-es256-key>"          { capabilities = ["update"] }
path "<kv-v2-mount>/data/<prefix>/*"        { capabilities = ["read"] }
```

创建 settings key 的 provisioning token 另需 key 管理权限，并必须使用
`vault write transit/keys/<settings-config-key> derived=true`。若 `derived=false` 或 ACL 缺失，server 启动期 self-check
会失败，运行期采样失败时 `/readyz` 返回 503 且 body 中 `keyprovider_ready` 为 unhealthy。JWT signing ACL
不由 settings keyprovider self-check 覆盖，生产发布前需用同一 runtime token 对 `transit/sign/<jwt-es256-key>`
做一次签名 smoke。

每个 allowlist binding 的 `<prefix>/.rss-readiness` 是保留 canary，必须与 binary/config 原子发布并可读；
不得把业务 secret 值当 canary，也不得给 sampler 额外 namespace。`deploy/smoke.sh` 在默认 all-Local
（或 Remote 且 SPIFFE fixture 齐全）时机器断言八条闭环：

1. **readyz 就绪**：轮询 `/health/v1/readyz` 至 200（PG healthy + Redis PING healthy + Vault Transit self-check + Vault KV canary + domain transport ready + 迁移完 + 池就绪），并断言 body 含 `redis_ready` / `keyprovider_ready` / `vault_secret_resolver_ready` / `s3_object_store_ready` / `domain_transport_ready`。
2. **healthz liveness**：`/health/v1/healthz` 恒 200。
3. **metrics 导出**：`/health/v1/metrics` 200 且 content-type `text/plain; version=0.0.4`（Prometheus exposition；`PromExporter::install` 随 `run()` 必装，端点与 `RSS_OTEL_ENDPOINT` 无关）。
4. **运行时加固**：`docker inspect` 验 `User=65532:65532` 且 `ReadonlyRootfs=true`。
5. **Vault/KeyProvider down 路径**：暂停 compose Vault 后轮询 `/readyz`，确认 `keyprovider_ready` 使响应降为 503；恢复 Vault 后回到 200。
6. **Vault KV-only down 路径**：保持 Vault/Transit 可达，仅禁用 KV mount；确认 `vault_secret_resolver_ready=unhealthy`、`keyprovider_ready=healthy` 且 `/readyz` 为 503；重建 mount/canary 后恢复 200。
7. **MinIO/S3 down 路径**：停止 compose MinIO 后轮询 `/readyz`，确认 `s3_object_store_ready` 使响应降为 503；恢复 MinIO 后回到 200。
8. **Redis down 路径**：停止 compose Redis 后轮询 `/readyz`，确认 `redis_ready` 使响应降为 503。

> **readyz 语义 / fail-closed**：`/readyz` 是所有探针的 **worst-of 聚合**——`configs_ready`（PG 池就绪，初值
> Down）· `redis_ready`（Redis PING，初始启动已 fail-fast，运行期 down → 503）· `domain_transport_ready`（仅本进程 outbound SPIFFE material，启动失败 fail-fast、运行期 material 不可用 → 503；不探测 peer）· `keyprovider_ready`（Vault Transit encrypt+decrypt + wrong-AAD fail-closed self-check / sampler，启动失败 fail-fast、运行期 down → 503）· `vault_secret_resolver_ready`（allowlist 同源的 KV v2 保留 canary；mount/ACL/canary down → 503，Forbidden 不写状态）· `rls_ready`（RLS 能力门）· `auth_grant_sweeper`（auth_grants 过期清理 worker，worker 停 → 503、sweep 失败 → Degraded）· `outbox_relay` / `event_consumer`（durable 事件 worker，#1251：worker 停
> → Unhealthy/503、relay 错误 → Degraded）· live saga contract 注册后出现的 `saga_executor:<owner>__<contract_slug>`
>（worker 停 → Unhealthy/503、source/store infra 错误 → Degraded；无 live registration 不注册假 probe）·
> `rss_access_token_jwks_ready` / `federated_access_token_jwks_ready`（启用对应 profile 时）：初始 JWKS 加载
> fail-fast；**刷新失败 → Degraded/`/readyz` 仍 200**（保留 last-good，不摘流量）。
> `rss_access_token_signing_rotation`（启用 `rss-access` 时，与 `outbox_relay` 同档拆分）：Active 或缺窗内
> Retiring 的 JWKS → **Unhealthy/503**；Retiring 已过 `verify_until` 的 cleanup debt → **Degraded/200**（不摘流量）；
> Next 缺 JWKS 仍可 **Healthy** 并带 detail。其余探针 **Unhealthy → 503**（fail-closed：未就绪不放流量）。裸镜像无 PG →
> 永远 503；PG/worker 就绪后转 200。`docker compose exec server sh` 不可用（distroless 无 shell，符合预期）——
> 排查用 `docker compose logs server` + `docker inspect`。

## 外部 delivery 探针契约

镜像**不内置 Docker HEALTHCHECK**（distroless 无 shell）。外部 delivery 系统应在受控内部
网络访问 Health listener：`/health/v1/healthz` 是 liveness，`/health/v1/readyz` 是接流量前的
worst-of readiness。具体调度资源和探针语法不由本仓库定义。

## 可观测性导出（Prometheus metrics + OTLP trace，#1253）

观测导出在组合根（`assemblies/runtime`）接线，**端点位置 ≠ Prometheus 默认**，必须显式配置：

### Prometheus scrape（`metrics_path` 非默认 `/metrics`）

`/metrics` 与 healthz/readyz 同挂 Health listener（8083），完整路径 **`/health/v1/metrics`**——Prometheus 默认
`scrape_path` 是 `/metrics`，**必须显式覆盖 `metrics_path`**，否则抓 `/metrics` 得 404、被记空抓取：

```yaml
# prometheus.yml scrape_config（受控内部 Prometheus）
scrape_configs:
  - job_name: rss-server
    metrics_path: /health/v1/metrics      # 非默认 /metrics，必须显式声明
    scheme: http
    static_configs:
      - targets: ["rss-server:8083"]       # Health listener 端口；仅内部可达
```

一致性 dashboard 不应从 `/health/v1/metrics` 之外的 ad hoc SQL 或日志面板补共享契约缺口。共享面板只使用
`docs/ops/202607082104-1642-consistency-dashboard-checklist.md` 列出的 server/runtime-exported metric；尚未导出的
inbox backlog 和 projection runtime 指标分别由 #1683 / #1684 落地 carrier 后再进入共享 dashboard。

**安全边界（匿名 NoAuth 面）**：Health listener（含 `/metrics`）是 `AuthScheme::NoAuth` 匿名面——**只在
loopback / 受控内部网络暴露，绝不经公网入口对外**。演示栈 8083 绑 `127.0.0.1`
落实；生产网络隔离与 scrape 访问控制由外部 delivery 系统负责。

### OTLP/gRPC trace 导出（`RSS_OTEL_ENDPOINT`，按需开启）

trace 导出**默认关闭**——`RSS_OTEL_ENDPOINT` 未设时仅 fmt 结构化日志（stdout），不导出 trace、零额外依赖。设置后
按 scheme 派发 typed endpoint（误配在启动接线期 fail-fast，**不静默退回 fmt**）：

| 值 | 行为 |
|----|------|
| 未设 | 仅 fmt 日志，不导出 trace（本地开发 / 无 collector 环境默认） |
| `https://collector.example:4317` | TLS（生产默认路径，tls-ring + webpki-roots） |
| `http://localhost:4317` | 明文，**仅 loopback host** 显式 opt-in（同主机 sidecar collector） |
| `http://collector.example:4317`（非 loopback 明文） | **启动 fail-fast**（零信任：明文不出本机） |
| 非 `http(s)` scheme | **启动 fail-fast** |

OTLP endpoint/TLS/insecure 是部署契约（对齐 OpenTelemetry Collector exporter 配置范式）；导出经 batch processor
后台线程，进程优雅关停时 flush 未导出 span（`ShutdownStack` 最后 drain）。

## 非 root / 只读 rootfs / 复现性

- **非 root**：runtime 基底 `:nonroot` 内置 uid 65532；Compose 再显式 `user` 审计加固。
- **只读 rootfs**：server 不写盘（日志走 stdout，rustls 无磁盘状态）；compose `read_only: true` + `tmpfs:/tmp`
  兜底，`cap_drop: [ALL]` + `no-new-privileges` 证明最小权限运行。
- **复现性**：base 镜像钉 tag（`rust:1.96.0-bookworm` = 工具链 channel；`cc-debian12:nonroot`）+ `--locked`
  锁 `Cargo.lock` + `cargo-chef` 钉版。**生产硬化**：再钉 base digest（`FROM ...@sha256:<digest>`，CI 中
  `docker buildx imagetools inspect` 解析后写回）。bit-for-bit 复现（`SOURCE_DATE_EPOCH` 等）超本切片范围，
  与 SBOM/cargo-dist 同族留作 follow-up。
