# CI cache writer 与工具安装策略（#1728）

> `INVARIANT: CI-CACHE-WRITER-01` 由 `cargo xtask verify` 检查 shared action、三个 workflow
> 的 writer 条件和 restore/cleanup/save 顺序。证据字段见
> [202607102010-1726-ci-evidence.md](202607102010-1726-ci-evidence.md)。

## Ownership

| Lane | 可写触发 | 其它触发 |
|------|----------|----------|
| CI | 受保护 `develop` 的 `push` | restore-only |
| Integration | 受保护 `develop` 的 `push` | restore-only |
| Audit | 受保护 `develop` 的 `schedule` | restore-only |

PR、fork PR、普通分支 push 和 `workflow_dispatch` 均不调用 save。资格由 workflow 的
`github.event_name`、`github.ref` 与 `github.ref_protected` 同时决定；不依赖 GitHub 对低信任
触发器的隐式只读行为。

## Cache 边界与 key

shared `setup-rss-ci` action 只执行 `actions/cache/restore@v4`，并输出 download/target/tools
三类物理 cache 的 primary key、matched key、exact-hit，以及聚合到 evidence 的 build/tools 落盘恢复体积：

- download cache：仅 `~/.cargo/registry/cache`、`~/.cargo/registry/index`、`~/.cargo/git/db`，
  不缓存解包后的 registry source 或 git checkout；
- target cache：`.cache/cargo-target`；
- tool cache：`.cache/ci-tools/<profile>`，不包含整个 `~/.cargo`、凭据或构建日志。

三类 cache 都只允许 exact restore，不设置 `restore-keys`。download key 绑定 schema epoch、lane、
runner OS/arch、Rust toolchain、profile，以及 `Cargo.lock`、`.cargo/config.toml`、
`rust-toolchain.toml` 的内容 hash；target key 另外绑定完整 Git tree identity；tool key 绑定安装 action
commit、binstall commit/version、精确工具 spec 与显式 epoch。key 不含 actor、ref 或 URL。

## Save lifecycle

所有 lane 设置 `CARGO_INCREMENTAL=0`。三条触发 workflow 是只含 trigger、权限和 literal lane 的薄
caller；唯一 lifecycle 位于 `.github/workflows/rss-rust-lane.yml`。受信 writer 按以下顺序执行：

1. shared action exact-restore 三类 cache；tool exact hit 只检查非 symlink 可执行布局，不通过执行缓存
   二进制来“自证”来源。
2. tool miss 由钉版 installer 安装并严格验证唯一精确版本；在任何 xtask/build.rs/test 运行前测量、执行
   5 GiB 门并显式保存 tool cache。之后不再保存 tool root。
3. xtask 成功后，`ci-cache-maintain.sh cleanup` 通过 `cargo metadata` 枚举 workspace package，执行 package-scoped
   clean，并删除剩余 `incremental` 目录；路径越界、symlink、metadata 或清理失败均 fail-closed。
4. `measure` 记录 download/target candidate，先执行 5 GiB 门，再写入 `before-save` evidence。
5. 分别以 exact primary key 保存安全 download 子目录与 source-bound target。
6. 写入 `after-save` evidence，再以 `always()` 上传 artifact。

save step 使用 `continue-on-error`，cache 服务不可用不覆盖代码门结果。官方 save action没有可证明
后端归属的输出，因此 `attempted-success` 仅表示 action step conclusion 为 success；它不宣称本 job
一定创建了 entry，也不区分并发 writer collision。

## 工具安装与供应链

- workflow 只接受严格的 `name@semver` 列表；空列表是合法 no-op，非法名称、参数注入形态和非完整
  semver 在下载前被拒绝。
- `taiki-e/install-action` 固定到 `v2.79.11` 对应 commit
  `13608cbb45b01feb47ef444ab1a42dc41ad56f1a`，且设置 `fallback: none`；受支持工具直接写入隔离
  tool root。
- `cargo-binstall` 固定到 `v1.20.1` 对应 commit
  `732870f031d2fb36309d0deaf36abcc704a7be65`。fallback 禁用 quick-install 与 telemetry，源码构建
  只写 `${RUNNER_TEMP}/rss-tool-build-target`，安装结果写入隔离 tool root。
- fresh install 才从隔离 root 执行 `--version`；解析必须以工具名和唯一精确 semver 开头，额外 semver、
  symlink、缺失或版本污染均 fail-closed。exact cache hit 不执行未建立本 job 来源信任的二进制，只检查
  root 内非 symlink executable 布局；cache 信任来自受保护 writer 在 repository execution 前的 immutable save。
- metadata、package clean、git tree 与 fresh version 命令失败时，诊断只输出闭集 stage、已验证 subject、
  exit code 与原因分类；不回显 raw stderr、secret、credential URL 或物理路径。

## 运维判断

先查看 evidence 的 restore result 与 footprint，再检查 `before-save` 的 candidate size 和 eligibility，
最后查看 `after-save` 的 attempted/skipped 与 step conclusion。不要把 restore footprint 当成网络传输字节，
也不要把 action success 当成后端持久化证明。cache 大小硬阈值不在本项引入；仍以 5 GiB runner 可用空间
为硬门，后续 SLO 只基于积累的 evidence 决定。
