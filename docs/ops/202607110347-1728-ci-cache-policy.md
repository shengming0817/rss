# CI cache writer 与工具安装策略（#1728）

> `INVARIANT: CI-CACHE-WRITER-01` 由 `cargo xtask verify` 检查 shared action、reusable workflow
> 与 caller workflow 的 writer 条件和 restore/save 顺序。证据字段见
> [202607102010-1726-ci-evidence.md](202607102010-1726-ci-evidence.md)。

## Ownership

| Job | 可写触发 | 其它触发 |
|-----|----------|----------|
| `ci-meta`、`ci-core-prerequisites`、`ci-security`、`ci-coverage` | 受保护 `develop` 的 `push` | restore-only |
| `ci-core-tests/1-of-2` | 受保护 `develop` 的 `push` | restore-only |
| `ci-core-tests/2-of-2` | 无 | restore-only |
| `integration/postgres-domain/unpartitioned` | 受保护 `develop` 的 `push` | restore-only |
| 其它 Integration job | 无 | restore-only |
| Audit | 受保护 `develop` 的 `schedule` | restore-only |

PR、fork PR、普通分支 push 和 `workflow_dispatch` 均不调用 save。资格由 workflow 的
`github.event_name`、`github.ref` 与 `github.ref_protected` 同时决定；同一矩阵只保留上述唯一 writer，
避免并发 job 竞争同一个 key。CI 与 Integration caller 对同一 PR 启用 concurrency cancellation，分支
运行不会互相取消。

## Cache 与 target 边界

可跨 job 持久化的内容只有三类：

- download cache：`~/.cargo/registry/cache`、`~/.cargo/registry/index`、`~/.cargo/git/db`，不含解包后的
  registry source、git checkout 或构建产物；
- tool cache：`.cache/ci-tools/<profile>`，只包含 catalog 声明并经 seal 验证的 executable；
- compiler cache：受信 Actions `restore`/`save` 持久化的独立 sccache disk cache，只保存 sccache
  内容寻址的不可变编译结果。

sccache 0.15.0 的原生 GHA backend 没有可用于本信任矩阵的只读模式，因此 RSS 明确不采用它。每个 job
运行 job-local disk backend；Actions cache 负责跨 job 持久化：download/tool使用exact restore，compiler cache
使用兼容前缀恢复最近的受信snapshot并以run/job唯一key保存。低信任运行只restore，
只有 Ownership 表中的受保护 writer 才 save。evidence 中的 `remote-read-only` / `remote-read-write` 表示
Actions 持久化权限，不表示 sccache server 直接访问远端 backend。

Cargo target 不是 cache。每个 CI job 都显式写 `$RUNNER_TEMP/rss-cargo-target`，不 restore、不 cleanup、
不 save；链接产物、build script、proc-macro、测试、JUnit、coverage 和 job evidence 因而保持 job-local。
本地默认 target 则由当前 worktree 的 `.cargo/config.toml` 解析为 `.cache/cargo-target`。shared setup
输出 target 的 resolved path 与 `ci-runner-temp` 来源，消费方不得自行推导共享路径。

download key 只绑定 schema epoch、runner OS/arch、Rust toolchain，以及 `Cargo.lock`、
`.cargo/config.toml`、`rust-toolchain.toml` 的内容 hash；不含 lane、profile、Git tree、actor、ref 或 URL。
tool key 绑定真实工具集合、catalog/adapter hash、钉版 installer 与 runner/toolchain identity。所有
download/tool的`actions/cache` restore使用exact key且不设置`restore-keys`；只有compiler cache允许固定兼容
前缀，前缀不含lane/profile/ref，且save资格仍由受保护writer条件控制。

## Compiler cache policy

工具 catalog 钉住 `sccache 0.15.0`；adapter 验证 canonical executable、完整版本输出和安装 seal，
错版或被替换的 cached binary 不可进入 typed Cargo/nextest funnel。启用 compiler cache 时：

- 清除任意 ambient `RUSTC_WRAPPER`，仅注入验证后的绝对 sccache 路径；
- 强制 `CARGO_INCREMENTAL=0`，避免 incremental 与 compiler cache 重复占用和不稳定交互；
- 每个 job 使用独立 server 生命周期和 job-local disk cache 工作目录，跨 job 只共享 Actions 持久化的
  缓存内容；
- backend/server I/O 错误按性能层降级，不重跑命令、不吞编译错误，也不改变 build/test verdict。

本地治理门以 Make 或 `hack/cargo.sh` 作为受控 bootstrap。默认 `RSS_COMPILER_CACHE=auto` 会按 PATH
顺序物理规范化并验证候选，跳过无效项；首个合法候选启用缓存，无合法候选则禁用缓存并继续普通
Cargo。`off` 显式禁用，未知值仍 fail-closed，不另设无 caller 的 strict/required 模式。direct
`cargo xtask` 只与受控入口共享 typed gate plan 和 worktree-local target 默认值，不共享外层 Cargo 的
build-jobs、ambient wrapper 清洗或 sccache 自动策略。

sccache 只在 compiler cache key 完全一致时命中。同一逻辑 checkout 路径与相同输入可复用；但
sccache 0.15.0 的 Rust hasher 会散列绝对 `cwd`，因此 RSS 不承诺自有 crate 跨不同绝对路径 worktree
命中，也不使用 `SCCACHE_BASEDIRS`、路径虚拟化或私有 fork 伪造该能力。

## Restore/save 生命周期

1. shared setup 创建job-local target，exact-restore download/tool，并按固定兼容前缀restore compiler disk cache。
2. tool exact hit 先验证 seal 和 binary digest；miss 由钉版 installer 安装，并在任何 repository code
   执行前完成 probe、seal、预算门和 tool save。
3. xtask 只通过 typed funnel运行 Cargo/nextest；compiler cache stats 在构建后采集为 evidence，采集失败
   仅记录闭合错误。
4. 代码门成功且 writer 资格成立时，测量并保存 download 与 compiler disk cache；完整 target 永不进入
   candidate 或 save。
5. save step 使用 `continue-on-error`，随后写 `after-save` evidence、stage、上传 artifact 并评估 SLO。

`attempted-success` 只表示 save action step conclusion 为 success；它不证明后端一定新建 entry，也不区分
并发 collision。restore footprint 与 candidate size 都是 runner 落盘测量值，不是网络传输量。

## 工具安装与供应链

`.github/scripts/ci-tool-catalog.txt` 是工具版本、安装 backend、受限相对路径与 probe 的机器单源；
workflow 和 shared action 不接受任意工具列表。未知 lane/backend、重复工具、backend 冲突、非完整 SemVer、
symlink executable、receipt 或 seal 不一致均 fail-closed。

`taiki-e/install-action` 和 `cargo-binstall` 使用仓库钉住的 immutable revision/version。fresh install 先由
上游 checksum 边界约束，再由 repository-owned adapter 验证；cache hit 不执行 binary 自证来源，而是核对
seal、catalog/adapter hash、完整请求集、受限相对路径和 SHA-256。seal 证明受信 writer 到 exact restore 的
完整性连续性，不替代上游发布真实性。

## 运维判断

先在 evidence 中确认 `download`/`tools` 的 restore/save 结果，再看 `compilerCache` 的 access、requests、
hits、misses、non-cacheable 与 errors；最后结合 target size、CPU time、peak RSS 和磁盘低水位判断收益与
资源压力。不要从 target 体积推断 compiler cache 命中，也不要把不同绝对 worktree 路径的 miss 视为回归。
