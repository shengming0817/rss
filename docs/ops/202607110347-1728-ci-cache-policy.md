# CI cache writer 与工具安装策略（#1728）

> `INVARIANT: CI-CACHE-WRITER-01` 由 `cargo xtask verify` 检查 shared action、reusable workflow
> 与三个 caller workflow 的 writer 条件和 restore/cleanup/save 顺序。证据字段见
> [202607102010-1726-ci-evidence.md](202607102010-1726-ci-evidence.md)。

## Ownership

| Lane | 可写触发 | 其它触发 |
|------|----------|----------|
| `ci-meta` | 受保护 `develop` 的 `push` | restore-only |
| `ci-core` | 受保护 `develop` 的 `push` | restore-only |
| `ci-security` | 受保护 `develop` 的 `push` | restore-only |
| `ci-coverage` | 受保护 `develop` 的 `push` | restore-only |
| Integration | 受保护 `develop` 的 `push` | restore-only |
| Audit | 受保护 `develop` 的 `schedule` | restore-only |

PR、fork PR、普通分支 push 和 `workflow_dispatch` 均不调用 save。资格由 workflow 的
`github.event_name`、`github.ref` 与 `github.ref_protected` 同时决定；不依赖 GitHub 对低信任
触发器的隐式只读行为。

## Cache 边界与 key

shared `setup-rss-ci` action 只执行 `actions/cache/restore@v4`，并输出 download/target/tools
三类物理 cache 的 primary key、matched key、exact-hit，以及聚合到 evidence 的 build/tools 落盘恢复体积：

- download cache：仅 `~/.cargo/registry/cache`、`~/.cargo/registry/index`、`~/.cargo/git/db`，
  不缓存解包后的 registry source 或 git checkout；
- target cache：`.cache/cargo-target`；
- tool cache：`.cache/ci-tools/<profile>`，不包含整个 `~/.cargo`、凭据或构建日志。

三类 cache 都只允许 exact restore，不设置 `restore-keys`。四条 CI lane 的 lane/profile 一一对应，
因此 download、target、tool 均拥有互不共享的 writer ownership 与 namespace。download key 绑定 schema epoch、lane、
runner OS/arch、Rust toolchain、profile，以及 `Cargo.lock`、`.cargo/config.toml`、
`rust-toolchain.toml` 的内容 hash；target key 另外绑定完整 Git tree identity；tool key 使用 v4 epoch，绑定
adapter catalog 内容 hash、安装 action commit、binstall commit/version 与 catalog 解析出的精确工具 spec。
key 不含 actor、ref 或 URL。

## Save lifecycle

所有 lane 设置 `CARGO_INCREMENTAL=0`。三个触发 workflow 是只含 trigger、权限和 literal lane 的薄
caller；其中 CI caller 精确声明四个 literal jobs，唯一 lifecycle 位于
`.github/workflows/rss-rust-lane.yml`。受信 writer 按以下顺序执行：

1. shared action exact-restore 三类 cache；tool exact hit 不执行缓存二进制，而是验证 v1 seal 中的 lane、
   adapter/catalog hash、完整请求集、受限相对路径与每个 binary SHA-256。
2. tool miss 由钉版 installer 安装，adapter 按每个工具的真实 probe/proof 协议严格验证唯一精确版本，
   全部成功后原子写入 v1 seal；在任何 xtask/build.rs/test 运行前确认 seal、测量、执行 5 GiB 门并显式
   保存 tool cache。之后不再保存 tool root。
3. xtask 成功后，`ci-cache-maintain.sh cleanup` 通过 `cargo metadata` 枚举 workspace package，执行 package-scoped
   clean，并删除剩余 `incremental` 目录；路径越界、symlink、metadata 或清理失败均 fail-closed。
4. `measure` 记录 download/target candidate，先执行 5 GiB 门，再写入 `before-save` evidence。
5. 分别以 exact primary key 保存安全 download 子目录与 source-bound target。
6. 写入 `after-save` evidence，再以 `always()` 上传 artifact。

save step 使用 `continue-on-error`，cache 服务不可用不覆盖代码门结果。官方 save action没有可证明
后端归属的输出，因此 `attempted-success` 仅表示 action step conclusion 为 success；它不宣称本 job
一定创建了 entry，也不区分并发 writer collision。

## 工具安装与供应链

- `.github/scripts/ci-tool-catalog.txt` 是工具版本、安装 backend、受限相对路径与 probe 的机器单源；shell
  adapter 直接读取，`xtask/build.rs` 在编译期从同一文件派生 evidence 版本与安装提示。README 只通过
  adapter 的 `specs` 输出展示 catalog，不复制版本表。

- executable adapter catalog 是工具版本、backend、binary、lane 和 probe/proof 协议的唯一事实源；workflow
  与 shared action 不接受任意工具列表。空工具 lane 是合法 no-op，未知 lane/backend、重复工具、backend
  冲突和非完整 SemVer 在下载前 fail-closed。
- `taiki-e/install-action` 固定到 `v2.82.0` 对应 commit
  `b8cecb83565409bcc297b2df6e77f030b2a468d5`，且设置 `fallback: none`；受支持工具直接写入隔离
  tool root。
- `cargo-binstall` 固定到 `v1.20.1` 对应 commit
  `732870f031d2fb36309d0deaf36abcc704a7be65`。fallback 禁用 quick-install 与 telemetry，源码构建
  只写 `${RUNNER_TEMP}/rss-tool-build-target`，安装结果写入隔离 tool root。
- fresh install 才执行隔离 root 中的工具：nextest 使用其多行版本协议，llvm-cov 与 dylint 使用子命令式
  probe，`dylint-link` 只核对 `.crates.toml` 的 package/version/registry source/bin receipt，绝不执行 linker
  wrapper。完整 SemVer、工具 identity、非 symlink executable 布局或 receipt 不一致均 fail-closed。
- install-action 上游会在自身 step 内把 checksum 已验证的 prebuilt 目录追加到 `GITHUB_PATH`，且没有关闭该行为的
  input；因此它固定为最后一个 installer step，下一步立即由 repository-owned adapter 完整验证，期间不运行
  repository code。RSS 自身的两条 tool PATH 仅在 adapter 验证成功后显式暴露。
- v1 seal 证明受保护 writer 完成 fresh 验证后到 exact restore 的完整性连续性；cache hit 通过 adapter 和
  binary digest 校验，不执行缓存 binary。它不证明已攻陷 writer 所产内容的真实性；上游真实性仍依赖
  immutable installer、上游 checksum 与受保护 writer。
- metadata、package clean、git tree 与 fresh version 命令失败时，诊断只输出闭集 stage、已验证 subject、
  exit code 与原因分类；tool layout 仅输出已验证的 `name@version`、受限相对路径及 missing/extra 计数，
  不回显 raw stderr、secret、credential URL、未知文件名或物理路径。

## 运维判断

先查看 evidence 的 restore result 与 footprint，再检查 `before-save` 的 candidate size 和 eligibility，
最后查看 `after-save` 的 attempted/skipped 与 step conclusion。不要把 restore footprint 当成网络传输字节，
也不要把 action success 当成后端持久化证明。cache 大小硬阈值不在本项引入；仍以 5 GiB runner 可用空间
为硬门，后续 SLO 只基于积累的 evidence 决定。
