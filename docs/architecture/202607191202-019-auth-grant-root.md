# ADR-019：AuthGrant 认证授权根与原子登录持久化

- **状态**：Accepted
- **日期**：2026-07-19
- **关联**：issue #1834、#1838；RSS grant claims 由 ADR-021 / #1835 交付；由 ADR-020 / #1841 扩展统一
  凭据安全事件关闭协议，后续 #1842、#1843
- **取代**：内部 `Session` / `SessionId` / `SessionLifecycle` 与独立初始 refresh 写入模型

> **ADR-021 amendment（#1835）**：为让 RSS issuer 的公开输入在类型层只能从 AuthGrant 派生，AuthGrant
> 聚合、`AuthnEpoch` 与完整 credential-security kind 词汇下沉 `authn`。identity 继续拥有 lifecycle port、
> 持久化命令、账户状态与安全事件事务能力；这不是第二个 grant 真源，也不改变本文的数据库/事务边界。

## 背景

旧 `Session` 只保存字符串 subject、租户、过期时间和 revoked 标志；refresh token 则独立保存
`PrincipalKind + subject`。数据库不能证明一个 refresh family 属于哪个认证根，也不能证明其用户、账户
authentication epoch 和根状态一致。登录又把 session/outbox 与初始 refresh 分开持久化，任一阶段失败都会形成
半成功状态。公开的初始 refresh 插入能力还允许绕过登录事务。

这不是给 `Session` 增加几个 nullable 字段即可修复的问题。认证成功产生的是一个有明确用户、认证时刻、账户
epoch、存续状态和关闭语义的授权根；refresh family 是该根的从属能力。

## 决策

### 四原则

1. **彻底**：内部模型、端口、PostgreSQL/memory provider、清理器和运维命名统一为 AuthGrant；登录一次提交
   根、初始 refresh 和 outbox，关闭一次撤销整个 refresh 族并关闭根。
2. **不向后兼容**：不保留旧类型 alias、表、列、函数、双读写或旧 binary 兼容。0070 在停旧 writer 后清空
   pre-GA session/refresh 数据并重建严格结构。
3. **优雅简洁**：`AuthGrantLifecycle` 只管创建/读取，所有终态安全 mutation 只进入
   `IdentitySecurityLifecycle`；`RefreshTokenStore` 只读。本 PR 只保持 HTTP/event 现有的 `sessionId` 与
   `identity.session-created` event wire；
   access JWT 的 `sid/jti/auth_time/authn_epoch` 已由 #1835 / ADR-021 交付，不把内部旧抽象带回领域。
4. **AI-HARD**：非法根状态由私有构造和闭值转换阻断；初始 refresh 无独立写端口；bearer 释放由线性 receipt
   阻断；跨根绑定和关闭顺序由复合外键/CHECK 在数据库提交点阻断。

### AuthGrant 状态机

authn 服务层拥有 AuthGrant 状态机；identity 域通过自己的 lifecycle port 持久化并执行事务。AuthGrant 以
`(tenant_id, grant_id)` 唯一标识，持有强类型 `UserId`、`auth_time`、
`authn_epoch_at_issue`、`expires_at`、状态和终态元数据。

| 状态 | `closed_at` / `close_reason` | 合法原因 |
|---|---|---|
| `Active` | 必须均为空 | 无 |
| `Revoked` | 必须均存在 | ADR-020 的账户级事件或 `LogoutCurrent` |
| `Compromised` | 必须均存在 | 仅 ADR-020 的 `RefreshReuseDetected` |

构造时要求 `auth_time <= issued_at < expires_at`。普通 `close` 只能从 Active 产生密封转换，关闭时间不得早于
issued/auth time。ADR-020 只为 refresh reuse 增加密封的 Active/Revoked→Compromised 提升；Compromised 为最高
终态，不能降级或借其他原因进入。`Compromised` 与 refresh reuse 一一对应，不增加没有业务语义的 migration
reason。敏感标识和 token hash 的 Debug 只输出脱敏形态。

### Refresh 是根的从属能力

每条 `RefreshTokenRecord` 必须保存 `tenant + AuthGrantId + UserId + authn_epoch_at_issue +
auth_grant_status`；删除 `PrincipalKind/kind/subject`。初始记录从 AuthGrant 生成，轮换 child 只能从密封
rotation 继承全部绑定，调用方不能改写用户、根或 epoch。

PostgreSQL 通过五列复合外键把 refresh 指回 AuthGrant：

```text
(tenant_id, auth_grant_id, user_id, authn_epoch_at_issue, auth_grant_status)
→
(tenant_id, grant_id, user_id, authn_epoch_at_issue, status)
```

外键使用 `ON UPDATE CASCADE ON DELETE CASCADE`。CHECK 要求非 revoked refresh 只能绑定 Active 根。因此直接
关闭仍有 active/consumed refresh 的根无法提交；合法关闭必须先撤销整个族，再更新根状态。

### 登录能力链与原子边界

登录按以下顺序执行：

1. credential 原子认证返回 Active 账户 receipt；
2. 构造 AuthGrant 和 `identity.session-created` generated fact；
3. `RefreshService::prepare_initial(&AuthGrant)` 重读账户 Active/epoch，只在内存生成 access/refresh bearer
   与哈希记录，不写存储；
4. crate-private constructor 创建 `LoginGrantMutation`，其中只有 AuthGrant、初始 refresh 哈希记录和线性
   pending-persistence capability；明文 bearer 保留在私有 `PendingLoginSecrets`；
5. `AuthGrantLifecycle::persist_login_grant` 必须同时接收精确 route producer receipt、mutation、
   `EventEntry` 与 envelope。PostgreSQL 在一个 `producer_tx` 中写根、初始 refresh 和 outbox；
6. provider 只有在事务成功确认后才把 mutation 内不可伪造的 pending capability 转成
   `PersistedLoginGrantReceipt`；`PendingLoginSecrets::release` 只接受该 receipt。

`PersistedLoginGrantReceipt` 的字段私有，外部不能构造。提交未知返回错误并丢弃 receipt，即使数据库最终可能
全提交，也不向客户端返回 bearer；数据库状态只能是三者全无或三者全有。L2 assurance 静态验证
producer receipt → generated fact → authorization → transaction outcome 的能力链，compile-fail 测试验证
mutation、persistence receipt 和 bearer release 边界不可伪造。

`RefreshTokenStore` 只保留既有 family 的查询，不提供 initial insert、`rotate` 或 `revoke_lineage`。
`AuthGrantLifecycle` 同样删除 `close`；不得用兼容 alias、默认方法或 adapter 固有方法重建旁路。

### Refresh conditional producer 能力链

`identity.refresh` 是 `identity.security-event` 的第五个 producer。路由生成的
`RefreshProducerReceipt` 与密封 `RefreshExecutionCommand` 一同进入唯一
`IdentitySecurityLifecycle::execute_refresh`：Active record 只能派生 Rotate，已验证存在的 non-Active
record 只能派生 ContainReuse，调用方不能替换 tenant/user/grant/epoch/lineage 或 close reason。

PostgreSQL 只执行一个 plain `producer_tx`，锁序固定为
`account-security → refresh-family → auth-grant → projection/outbox`。正常轮换原子 consume old + insert child，
返回 `NoMutation` 且不发事件；reuse winner 在同一事务撤销 exact family、单调提升 grant 为 Compromised 并
append 一条 `RefreshReuseDetected`，重复检测返回 AlreadyContained 且不重复事件。任一步失败整体回滚，
commit unknown 不自动重试，也不能生成 persisted receipt。

新 access JWT 与 refresh bearer 留在私有 `PendingRotatedSecrets`。只有
`Applied(PersistedRefreshRotationReceipt)` 能消费 pending value 并 release；reuse、stale、expired、rollback
或 commit unknown 在类型层拿不到 bearer。

### 关闭与账户 fence

终态转换由 ADR-020 的密封 security command 产生。security lifecycle provider 在一个事务中先把该根的
refresh family 置为 revoked，再更新 AuthGrant；数据库 CHECK/FK 对错误顺序 fail closed。ADR-020 将当前会话、
账户级批量关闭与 refresh reuse 收敛为唯一事件模型，并把共事务锁序固定为
`account-security → refresh-family → auth-grant`；账户级事件先递增 epoch，再按该顺序关闭全部活动根，grant 级
事件保持 epoch 不变。生产 logout/reuse 入口与跨边界传播仍由 #1842/#1843 挂载。

refresh 查询和 rotation 同时要求根仍为 Active，并继续执行 ADR-018 的账户 Active + issuance epoch fence；
关闭或受损根、账户 epoch 漂移都不能 mint 或提交 child。

### 0070 与运维能力

0070 是 non-rolling、forward-only 迁移：

- 锁定旧写入，删除旧 refresh/session 数据和表/函数/maintenance role；
- 新建严格 `auth_grants` 与 `refresh_tokens`，所有绑定列 NOT NULL；
- 两表启用并强制 RLS；`rss_app` 没有 AuthGrant DELETE；
- 全域过期清理由固定 `rss_sweep_expired_auth_grants()` 承担，owner 为 NOLOGIN/BYPASSRLS
  `rss_auth_grant_maintenance`，应用只获 EXECUTE；
- runtime probe 与环境变量只保留 `auth_grant_sweeper` /
  `RSS_AUTH_GRANT_SWEEP_INTERVAL_MS`。

迁移成功后不得启动旧 binary、重建 sessions、恢复旧 operational 名称或手工补造 refresh 绑定。完整探针和
失败恢复流程见 migration README 的 0070 runbook。

## 设计对照

- [Tower Sessions `SessionStore`](https://github.com/maxcountryman/tower-sessions/blob/main/tower-sessions-core/src/session_store.rs)
  把 create/save/load/delete 收敛在同一 store，支持本决策的“生命周期同源”。RSS 不采用其通用 session
  record 作为认证模型，因为它不表达账户 epoch、refresh family 绑定或业务 outbox 原子提交。
- [Keycloak 管理会话文档](https://www.keycloak.org/docs/latest/server_admin/index.html#_user-session-management)
  把 refresh token 绑定到 user/client session，支持 session 状态作为 refresh 有效性的根；其 refresh rotation
  可配置，而 RSS 对本协议固定一次性轮换与 reuse compromise，并用数据库复合约束持续验证绑定。
- [Ory Fosite OAuth2 storage interfaces](https://github.com/ory/fosite/blob/master/handler/oauth2/storage.go)
  明确提供 create/get/delete/rotate refresh token session 操作，支持把 rotation 视为存储原子能力。RSS 进一步
  删除独立 initial create 端口，把首次写入收进 AuthGrant + outbox 登录事务。

## 被拒绝方案

- **给 sessions/refresh 增 nullable 列并回填**：旧数据无法证明 canonical UserId、签发 epoch 和根绑定；猜测
  回填制造虚假安全证据。
- **保留 Session alias 或双读写**：延长两个领域真源，允许新代码继续依赖失效抽象。
- **先持久化根/outbox，再独立 insert refresh**：保留 #1838 的半成功窗口。
- **mutation 携带明文 bearer**：provider、日志或 Debug 面不必要地接触 bearer secret。
- **应用检查替代数据库约束**：原始 SQL、旧任务或未来 adapter 可绕过，不能构成持续不变量。
- **根关闭后异步撤销 refresh**：在窗口内仍可轮换，也会被复合 FK/CHECK 正确拒绝。

## AI-HARD 载体

| 不变式 | 载体 | 评级 |
|---|---|---|
| 外部不能构造非法 AuthGrant 状态/时间/原因 | 私有字段 + checked hydrate/new/close | Hard |
| refresh child 不能改写根/user/epoch | 私有字段 + sealed rotation 继承 | Hard |
| refresh 不能独立写入或关闭 grant | `RefreshTokenStore` 纯 reader；删除 rotate/revoke_lineage/close | Hard |
| bearer 不能在持久化确认前释放 | 私有 pending secrets + 不可伪造 persisted receipt + typestate | Hard |
| login/security producer proof 必须闭合进唯一 `producer_tx` | sealed producer authorization + exact EventEntry/receipt signature | Hard |
| refresh mint 结果不能在 commit 确认前释放 | private pending secrets + persisted receipt typestate | Hard |
| refresh 不能错绑 tenant/user/epoch/status/root | 五列复合 FK + NOT NULL + CHECK | 数据库 Hard |
| 非 revoked refresh 存在时根不能关闭 | refresh/root status CHECK + FK cascade update | 数据库 Hard |
| Active/Revoked/Compromised 与关闭元数据一致 | Rust 状态机 +数据库 CHECK | Hard |
| 跨租数据不能读写，应用不能直接删根 | FORCE RLS + 精确 ACL | 数据库 Hard |
| 登录任一写入失败或提交未知不返回 bearer | fault injection + all-or-none PostgreSQL tests | Medium |
| security command CAS 冲突或提交未知不返回 receipt、不自动重试 | sealed command/receipt + PostgreSQL fault/concurrency tests | Medium |

本决策不建立 Soft-only 安全约束。
